# 三人协作执行手册

更新时间：2026-09-11。对应决策：D008 三人岗位冻结、D010 软件工作量分担规则。

## 一 手册用途

本手册规定三人团队每个工作日如何领任务、写代码、复核和交付，属于日常执行层文件。配套文件分工如下：

- `角色分工.md` 定义谁负责什么、谁复核什么。
- `Git协作规范.md` 定义分支用法（直推 `develop`）、提交信息、推送前检查和复核要求。
- `变更与决策流程.md` 定义公共接口和重大变更如何审批。
- `测试验收标准.md` 定义 L0 至 L7 验证等级。
- `板级硬件事实.md` §三补2 定义共享板卡与仪器的使用注意（**不编号、不登记、不设配额**）。

出现冲突时，职责范围以 `角色分工.md` 为准，日常流程以本手册为准，验证等级以 `测试验收标准.md` 为准。

## 二 岗位与决策权

| 项目 | M1 音频算法与竞赛交付 | M2 FPGA技术与系统集成 | M3 实体硬件与上板验证 |
|---|---|---|---|
| 所有权核心 | 算法定义、黄金模型、算法 RTL 行为、逐样本验证 | 时钟、CDC、接口、顶层、约束、构建与时序收敛 | 供电、电平、接线、传感器、仪器实测 |
| 主要交付物 | 模型、算法 RTL、验证报告、竞赛报告与答辩材料 | 工程、约束、综合与时序报告、稳定码流 | 接线与引脚表、测量数据、上板验证脚本 |
| 技术决策权 | 定点格式、音色结构、验收阈值 | 时钟与复位方案、FIFO 与 CDC 结构、I2S 实现、构建流程 | 选型与接线、电平方案、测量方法 |
| 一票否决 | 算法结果与模型不符或未逐样本验证 | 时序未收敛或 CDC 未做专项检查 | 存在电气安全风险或电平未核对 |

补充说明：

- 数字效果器（延迟、合唱）属于算法，由 M1 负责；跨采样率切换和跨时钟域部分由 M2 参与。
- I2S 数字发送属于接口时序与约束问题，由 M2 负责，M1 提供 PCM 数据格式和位宽要求。
- M2 兼任技术与集成负责人，负责维护 `main` 上稳定码流与提交的对应关系。
- M3 负责的上位机和仪器软件只用于测量、采集和自动化，不得替代 FPGA 生成正式音频。

## 三 共同决策事项

以下事项不能由 AI 或任一队员自行修改，必须走 `变更与决策流程.md` 并由 M2 发布：

- 公共演奏事件接口的字段、位宽和握手。
- PCM 输出接口、内部数据位宽和定点格式。
- 系统时钟、PLL 配置、复位方式和 `sample_tick` 约定。
- 顶层端口、CST 引脚和 I/O 电压。
- 最大复音架构、声部状态布局和正式音色数量。
- 正式 DAC 与输出链路、最终交互方案、最终显示方案。
- 新增会显著占用 DSP、BSRAM 或 DDR3 的功能。

| `code/rtl/audio_out/`（I2S 数字发送） | M2 | 自审 |
| `code/rtl/board/`、`code/rtl/common/`、顶层模块、`code/constraints/`、`code/sim/` | M2 | 自审 |
| `code/rtl/input/` | M3 | M2 |
| `code/software/`、`code/scripts/`（串口、仪器、采集） | M3 | M2 |
| `prep/脚本/` 中对应的 Word 生成脚本 | 文档发起人 | M2 |
| `code/docs/`、`README.md`、`.github/` | 任务单指定 | M2 |

**复核人统一为 M2（D025，2026-09-16）**：M2 自己主责的目录标「自审」，不再要求第二人复核。
本表只界定谁可以改，**不表示需要按分支隔离**——三人一律直接推 `develop`。

**八处共享文件的保护手段分两组**（D025 §3.3 + D026 + D027）：

- **接口组**：`code/rtl/board/electronic_piano_top.sv`、
  `code/rtl/common/audio_defs_pkg.sv`、`code/constraints/electronic_piano.cst`、
  `code/docs/模块接口规范.md`。**改动前必须在群里说一句**——并发重写同一个文件的
  代价高，而且改动会波及另外两人的模块。
- **编号表组**：`code/docs/验证记录.md`、`code/docs/技术决策记录.md`、
  `code/docs/任务看板.md`、`code/docs/当前状态.md`。**不需要提前说明**。
  这一组不属于任何一个人的目录，三个岗位都要往里追加，也是本项目两次编号撞号的
  实际发生地；但它的事故成因是**取号时机**，由下面「编号只在推送前最后一步取」
  针对，改前说一句并不传递「我要用哪个号」，拦不住撞号。

**编号只在推送前最后一步取（D026）**

开工不写、干活不写、功能提交里不带编号。顺序固定为：`git fetch origin` →
`git pull --rebase origin develop` → 看编号表末尾 → **现在才**写 `V00xx`／`D0xx`／
`T0xx` → 做成一个只含编号的独立小提交 → 立刻推送。取号与推送之间不要隔夜。

需要跨目录修改时先停止，列出受影响文件和原因，由相关两名负责人确认后扩大授权，不得自行扩大写入范围。

## 五 单任务执行流程

1. 在 `任务看板.md` 找到分配给自己且状态为待开始或进行中的任务编号。
2. 按 `协作入口.md` 的顺序读完必读文件，再读本岗位局部 `AGENTS.md`。
3. `git fetch origin` 后 `git pull --rebase origin develop`，保证在最新 `develop` 上开工。
   **不要新建功能分支**（D025）。
4. 先写参考模型或测试，再写实现，改动保持在任务授权范围内。
5. 运行模块自检，确认自动 PASS，并记录验证等级。
6. 自查接口、时钟、复位、位宽和约束是否与文档一致。
7. 运行 `.\code\scripts\check_repo.ps1`，**必须全 PASS 才能推送**。
8. **最后一步取号（D026）**：`git fetch origin` → `git pull --rebase origin develop` →
   看编号表末尾 → **现在才**写 `V00xx`／`D0xx`／`T0xx` → 做成一个只含编号的独立小提交。
   开工时不写编号，功能提交里也不带编号。
9. 直接推 `develop`：`git push origin develop`。被拒时先 `git pull --rebase`，不要用 `--force`。
10. 通知 M2 复核；M2 自己主责的任务标「自审」。**复核通过不强制留痕**，发现问题才补一行验证记录。
11. 更新 `当前状态.md`、`任务看板.md`。（板卡与仪器不编号、不登记、不设配额，见 D024，无需登记设备使用。）

## 六 复核规则

**2026-09-16 起按 D025 改为「复核归口 M2」：**

- **复核人统一为 M2。** M1、M3 推送后由 M2 复核该次推送的 diff；**一般没问题即通过**，
  发现问题由 M2 提出、作者修正。
- **M2 自己主责的改动标记「自审」**，不再要求第二人复核；在任务看板或提交信息中注明即可。
- **不强制留痕。** 复核通过时不写验证记录行；**只有发现问题时才补一行**说明问题与处理。
  注意区分：**任务自身完成时的验证等级行仍然必需**，那是 L0 至 L7 的唯一记录。
- 复核人必须实际查看 diff 或运行测试，不得只读代码就签字，也不得把未执行的阶段写成已通过。
- 复核人发现问题时提出退回意见，**不得直接代写实现**。
- 涉及时钟、复位、CDC、FIFO 或引脚时，复核人必须确认专项检查已完成。

复核重点清单：

- 是否只修改了授权目录。
- 接口和位宽是否与 `模块接口规范.md` 一致。
- 是否有自动判定 PASS 的测试，容差是否写明。
- 定点格式、舍入和饱和策略是否有说明。
- 是否新增未解释的 lint 警告或时序违例。
- 文档和约束是否同步更新。

## 七 软件工作量过多时的分担规则

算法模型、验证脚本、上位机和报告脚本都算软件工作量。当 M1 的软件任务积压并影响关键路径时，按 D010 启动分担，由 M1 在任务看板上提出并注明分担范围。

| 分担人 | 可以承担 | 不可承担 |
|---|---|---|
| M2 | 算法 RTL 的流水线划分、资源优化、FIFO 与 CDC 实现、I2S 与构建脚本 | 算法数学定义、验收阈值 |
| M3 | 按键与传感器驱动、串口协议、仪器控制、数据采集与自动化脚本 | 算法数学定义、验收阈值 |

分担后仍由 M1 负责算法数学定义、黄金模型口径和最终验收。分担人完成的代码按第四节的目录归属确定复核人（D025 后统一为 M2），验证等级不得降低。

**跨岗位代做的消息交接**：本规则也适用于 M2 代做 M3 工作、M3 代做 M1 工作等所有跨岗位代做，不限于 D010 软件分担。开工前按第四节取得对应授权；需要告知 M1/M3 时，代做人先向用户提供可直接私发的消息，写清代做范围和涉及文件。每完成一个可交付阶段，再提供一条交接消息，列出任务与已做内容、改动文件、提交号（未提交应明示）、运行命令与实际验证结果和等级、未完成/未上板项目、原负责人要继续处理的事项；向用户标注“待用户转发，尚未送达”。用户确认已私发给对应负责人后方可称“已通知”，M2 内部窗口同步、文档更新、推送与复核均不能代替交接。此规则不扩大写入权限，也不替代接口组文件的事前说明。

## 八 同步点与集成窗口

- 每周固定一次三方同步，确认任务看板状态、资源占用和下周集成窗口，并把结论写入 `每周同步记录.md`。
- 共同集成时段优先安排跨模块联调和上板验证。
- 集成窗口开始前，参与方必须先把各自模块推进到 L2 以上。
- 同步点 S1 至 S7 的定义见 `抉择与并行开发顺序.md`，每个同步点由三人共同验收，验收结论登记在 `每周同步记录.md`。

## 九 阻塞与升级

1. 遇到技术阻塞时，先在任务看板把状态改为阻塞，写明原因和已尝试的方案。
2. 阻塞超过一个工作日且影响关键路径时，提交三方同步讨论。
3. 涉及公共接口、时钟、复位、引脚或资源占用的阻塞，按变更流程提案，不自行绕过。
4. 影响安全、供电或可能损坏硬件时，任何人可立即停止实验，事后补记录。

## 十 任务交接清单

交接时至少提供以下内容，缺项视为未交接：

- 最新提交号（**不写分支名**，2026-09-16 起不再有功能分支，见 D025）。
- 已完成内容与当前验证等级。
- 运行命令和本次实际结果。
- 未验证的硬件相关项目。
- 当前占用的板卡、仪器和时段。
- 已知风险、临时绕行方案和下一步建议。

向 AI 交接时改用 `AI交接上下文.md` 中的标准提示词，避免把聊天记录当作事实来源。

## 十一 禁止事项

- 直接在 `main` 上开发或提交。
- 未经确认修改公共接口、时钟、复位、位宽、采样率、顶层端口或引脚。
- 把仿真通过写成上板通过，或跳过验证等级描述。
- 把未通过测试的码流标记为稳定版。
- 长期占用板卡或仪器而不登记。
- 让上位机或树莓派替代 FPGA 生成正式音频。
