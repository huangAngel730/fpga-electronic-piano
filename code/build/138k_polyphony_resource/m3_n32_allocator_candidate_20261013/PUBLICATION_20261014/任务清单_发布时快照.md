## 十七、审核与版本防漂移

审核流程：实现窗口自审 → 同一精确版本同时送审核员和预审员 → 审核员汇总唯一结论 → 原实现窗口修复具体阻断 → 修后只核增量和对应反例 → 完整阶段一次交 M2。

每个阶段的计划和结果使用不同 Review-Key：

```text
T061-N32-A-PLAN-R01
T061-N32-A-RESULT-R01
```

统一要求：

1. 一个 Review-Key 只绑定一个任务、阶段、修订和不可变快照；
2. 消息带完整版本指纹：仓库、基线、目标或封存包、范围 SHA、证据 SHA、工作区状态；
3. 审核员和预审员只审同一 Review-Key、同一完整指纹；
4. 先完成一方只进入 `WAITING-PEER`，预审员不单独宣布最终通过；
5. 审核员维护唯一队列并发布唯一汇总结论；
6. 源码、配置、测试、日志或关键证据变化均升版；
7. 新版收件后旧版为 `SUPERSEDED`，迟到消息为 `STALE`；
8. 不跨版本拼接审核、预审、日志或测试结论；
9. 返工附“发现 ID → 修改位置 → 反例结果 → 状态”映射；
10. 审核 PASS 不等于 M2 签收或新增执行许可。

两个审核窗口可直接通信；消息送达不等于对方已经处理，也不等于真人队员已通知。发生协作冲突、无法定位版本或权限争议时再请用户介入。

每个阶段只交一个精确版本：
