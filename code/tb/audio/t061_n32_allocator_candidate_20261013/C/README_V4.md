# N32-C 压力与恢复 v4

本后继由主对话2接管，只使用已经通过的 N32-B / R1 源快照。旧 v3 计划、
checker、软件夹具和失败证据保留。实际结果以本目录最终 RESULT 和封存为准。

v4 修复了实际执行前发现的几项问题：

- Release 要有 4800 次真实 sample 推进，不能用软件 tick 或等待代替。
- HOLD 时公开 READ 被背压；先观察阻塞，再撤 READ、释放 HOLD，之后读回。
- 事件完成等待公开 event_ready；NoteOff 的短暂 IDLE 还可能有释放扫描。
- 退休保留身份等槽元数据；真实退休的 pre-NBA 时点按冻结 Router 模型核验。
- READ 对比 B1 已配置／已提交银行上下文，包含 PCM 高 24 位。
- 输入黄金先由冻结 Router／ADSR／DDS／ROM 计算，再运行实际 RTL。
- 一万余刺激操作改用 128-bit 命令表和固定循环派发，避免 Icarus 展开大量 task。

执行顺序：`c_assets.py` 生成新资产目录，`c_capsule.py prepare` 冻结精确依赖，
再从快照内以 `-I -S -B` 执行 `c_capsule.py execute`。每个执行清单只调用各步一次，
独立输出目录拒绝覆盖。实际完整 argv、输入 SHA、stdout/stderr、退出码和前后身份
均在机器清单和收据中。普通实现修复必须使用新版本和新目录。

2026-10-14 用户明确将延时授权扩展到 C：持续推进至完成，卡住即停。
编译保留 300 秒限制，仿真／检查器另设 24 小时紧急上限。仿真连续 300 秒没有
公开 trace 增长即停止（CPU 忙不能掩盖零时间振荡）；静默软件检查器连续
300 秒既无 CPU 进展也无日志增长即停止。没有自动重试、换工具或设备操作。

`check_v4.py` 保留冻结 B2C 的逐沿独立数学与源码日历核验，同时核对 C 输入顺序、
公开控制快照、READ、HOLD、取消、复位和退休观察。完整原始 capture 的定向软件
变异由同一个检查器指定拒收。真实后端左右同值，单纯交换左右不会改变值；
使用单边 1 LSB 变异证明声道值检查，并如实保留交换本身不可观测的边界。

本阶段只产生独立候选功能／数学证据。Gowin、资源准入、PnR、物理 40 MHz STA、
正式顶层接入和设备验证仍未运行；完整 T061 保持 PARTIAL。
