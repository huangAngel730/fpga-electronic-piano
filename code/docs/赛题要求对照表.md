## 一 设计要求（总纲）

> 设计一套基于 FPGA 的实时多音色合成电子乐器引擎。系统依托电容触摸、光电感应、压力检测、无接触手势等任意自研交互方案，实现至少 2 个独立可控演奏维度的动作采集，精准识别选音、和弦、触发、拨弦等演奏指令。以 FPGA 为核心并行计算平台，在硬件逻辑层搭建专属实时音频合成引擎，采用波表采样、加法合成、FM 调频或物理建模等任意合规算法，对演奏控制信号进行逐样本、逐声部实时音频运算，最终通过 I2S 接口输出音频信号至 DAC 解码发声。

## 四 核心评分规则与现场验证标准

**这是全文最关键的一节，直接决定得分。**

### 4.1 振荡器统计规则

> 独立发声单元为包含独立相位累加器、频率调控、包络控制的完整振荡器；单波表采样查表不计多谐波数量，仅计单个振荡器；加法合成按运算分量统计、FM 按调制运算器统计、物理建模按并行弦/模态单元统计。

| 要点 | 覆盖情况 | 差距 |
|---|---|---|
| 振荡器定义：相位累加器 + 频率调控 + 包络控制 | **未记录** | **见 G10** |
| 单波表查表仅计 1 个振荡器 | **未记录** | **见 G10** |
| 加法合成按分量统计 | **未记录** | **见 G6** |
| FM 按调制运算器统计 | **未记录** | **见 G6** |

**影响**：这条决定**哪种架构得分更高**。

- 当前 D004 路线（DDS + 单周期波表）：32 个声部 = 32 个振荡器（波表内 2048 个谐波**不计**）
- 若改用**加法合成**：每个正弦分量独立计数，32 路正弦远多于 32 个波表振荡器
- 若用 **FM**：按调制运算器统计

三种路线的**得分效率不同**，而当前项目**未做此论证**就冻结了 D004。这不一定是错误（波表路线资源效率高、复音容易做多），但**缺少书面依据**。

### 4.2 系统吞吐量指标

> 以「同时活跃可闻独立振荡器总数 × 实际音频输出采样率」为核心评分依据，过采样不叠加加分。

| 要点 | 覆盖情况 | 差距 |
|---|---|---|
| **吞吐量 = 振荡器数 × 采样率** | **完全遗漏** | **见 G7，最高优先级** |
| 过采样不叠加加分 | 未记录 | 见 G7 |

**影响**：

- 这是**核心评分依据**，但项目文档中**从未出现此公式**
- 当前规划值：32 振荡器 × 48 kHz = **1.536 M 振荡器·采样/秒**
- 提高采样率同样能提升该指标，但"过采样不叠加加分"限制了粗暴提采样率的收益，**含义需要在报告中谨慎解读并避免误用**
- 该指标应在报告中作为**核心 KPI 单独列出**

### 4.3 现场验证要求

> 支持测试模式下输出多路不同频率音频，频谱可观测对应数量独立谱峰，同时可通过 RTL 代码佐证纯硬件实时合成通路，验证无预录音频播放行为。

| 要点 | 覆盖情况 | 任务 | 差距 |
|---|---|---|---|
| **测试模式输出多路不同频率** | **遗漏** | **T052**（2026-09-16 新增，W4，M1 主责 / M2 配合） | **见 G11** |
| **频谱可观测 N 个独立谱峰** | **遗漏** | **T052**（T032 只做分析工具） | 见 G11 |
| RTL 代码佐证纯硬件通路 | 部分覆盖 | 源码本身可佐证 + **T052** 出「测试模式 + 独立峰 + 活跃声部计数 + 削波计数」证据包 | 需在报告中组织 |
| 验证无预录音频 | 已覆盖 | `项目事实与范围.md` 明确不允许 + **T052** 以任意频率实时发声佐证 | 无 |

**影响**：现场答辩时评委会**按谱峰数量核对复音数**。没有测试模式就无法自证。这是一个**必须实现的交付功能**，已立 **T052**（2026-09-16）。

**⚠️ 一条容易踩的硬约束，出自本文档 §4.1「振荡器统计规则」**：「单波表采样查表**不计多谐波数量**，仅计单个振荡器」。这意味着**谱峰数与振荡器数必须 1:1**，因此测试模式**必须用纯正弦**：

- 若用带谐波的波形（锯齿/方波），一个波表振荡器会产生多个谱峰 —— **峰数 > 振荡器数，形同虚报复音数**；
- 若为了拉开频率而让谐波互相重合（如 200 Hz 的 2 次谐波恰为 400 Hz），则 **峰数 < 振荡器数，自证失败**。

两种方向都会让现场核对给出错误结论，所以纯正弦不是保守选择，而是**正确性要求**。

## 六 结论

1. **基础要求 3（合规实时发声与多复音）覆盖完整**，接口 v1.0 与之匹配良好。
2. **基础要求 1（多维交互）仍待验收**：电子钢琴式方案层已确定；实物 Velocity、CC64、MIDI 输入电平与端到端延迟尚需 T036 实测。
3. **核心评分规则一节整体缺失**：吞吐量 KPI、振荡器统计口径、现场验证模式三项均未进入任何文档或任务。这不是执行问题，而是**需求识别遗漏**。
4. 拓展要求中，效果器（延迟）和音色切换已覆盖；可视化反馈与滑音颤音未覆盖。

**建议动作顺序**：先补 G7 与 G10（文档级，成本低），再决策 G11 与 G1（需要新增任务），最后评估 G6（架构论证，影响资源规划）。
