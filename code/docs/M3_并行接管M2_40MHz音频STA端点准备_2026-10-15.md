## 一次交付的四项成果

1. **实际对象目录。**只读解析本次原报告/网表，按来源 SHA 列出新音频层级中可观测的 pitch-mod、声部→混音及 PCM/I2S 周边候选路径；每项记录实际起点、终点、时钟、Setup/Hold 是否在现有报告显示、相关原文位置及未查到的对象。严格区分“源码有 `base_s1/base_s2`”、“布局后网表有对象”与“已有明确端点对的双向定向报告”。定位不到目标时写 `UNKNOWN`，不可造目标名。控制规模：先以最关键的 pitch-mod 成对端点和至少一条真正音频路径为证，避免扫描全芯片做大项目。
2. **定向报告方案。**草拟仅用于隔离副本的 `report_timing -setup` / `-hold` 对象查询/目标命令，写明必须存在的 get_regs 对象、sys_clk 关联、非空实际路径、起止点和非负 slack，兼顾 absent/inactive 的失败处理。**只写提案文本，不把命令插入现行正式 SDC，不要求恢复旧 LOC。**若原寄存器已被综合优化，给对应真实关键端点建议和需要 M2 决策的差异，而不宣称旧名路径仍在。
3. **独立软件验收器和坏报告反例。**用新目录脚本检查被指定的端点对/时钟/setup+hold/活动状态、输入报告 SHA 和来源；给最少四个独立负例：缺端点、inactive、只有不相干音频路径、仅 Setup/仅 Hold，逐项实际命令、退出码、原 stdout/stderr、源 SHA。软件脚本不得以“报告任意音频路径出现”为总体 PASS；旧 checker 不改。
4. **有界交付。**一份易读结论及原始观察片段/脚本/fixture/收据/封包 SHA。明确是否有现成报告足以支持**限定**端点事实、需新 STA 的具体对象/命令、未签的范围；不把解析测试算成新 L5。保留旧失败，`board_release_allowed=false`。完整功能提交需按本机 Git 规则逐文件单独 `git add 路径`、9/9 门禁，最后 fetch 取号由 M2 统一登记。M3 不更新共享编号/状态表。
