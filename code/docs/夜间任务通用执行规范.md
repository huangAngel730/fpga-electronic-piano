# 夜间任务通用执行规范

## 2026-10-17 用户更正：每人从实际开工起最长5小时

本轮用户明确将夜间上限改为每人从实际START起最长5小时，当前R10及后续夜间单均适用；原06:30硬截止仍取较早者，已开工按原START计算剩余，不因换窗口/转轨/本次修订重新计时。5小时覆盖实现、验证、清理和交接，必要结果达到或无可行动项提前结束。三岗独立大板块、依赖、写集、工具次数/秒级预算及已消费记录不变；旧6小时及历史八小时实例不再决定当前可用时长。详见夜间任务通用执行规范与当前R10五小时卡。

## 一、适用顺序与边界

每次以用户当轮指令、最新有效岗位任务单和项目事实确定任务顺序、写集、完成条件、工具预算与许可。本规范统一执行和 GitHub 接力方法，不自动批准新任务、跨岗位代做、共享接口变更、EDA 次数、板卡操作或正式集成。

**夜间已授权任务的 GitHub 自动收件，覆盖旧规范和旧任务单中“必须用户私发／转发才算 AI 收到”“只能次晨交接”“等待队员或用户催促才继续”的冲突要求。**接收方应按第五节核验并留回执，不等待真人转发。此例外只改变 AI 收件方式；不能据此声称已通知真人、已在群里说明、已获准入或复核通过。需要用户新授权、接口组事前说明、M1 算法确认、M2 最终复核或真实执行许可时，仍停在对应边界。

既有任务的整包验收、发布门禁、禁止发布／统一串行发布的具体限制继续有效，不临时拆小冒称完成。之后的当晚任务单可预先定义能独立验收、下游可消费的完整交接单元，按其自身完成条件结项。2026-10-15 的三份夜间单及后续岗位单只提供当时条件，不自动继承其时间、工具身份、预算或旧通信方式；历史执行证据不改写。

## 二、开工前写出一页可自主执行的任务单

任务单在开工前入仓，标题给岗位、日期、计划版本和时间盒。至少填清以下内容：

| 必填项 | 要写清的内容 |
| --- | --- |
| 项目目标与优先级 | 最新总览和岗位单、当前关键路径、并行准备与明确暂缓项。 |
| 可用条件 | 用户／成员可回复时段、实物、工具、许可证、输入字节。每晚实核，有板不等于可下载。 |
| 时间与接收安排 | 总时长上限、三岗实际可用窗口、接收／复核责任人及其结束时间。下游仍需准入时，安排重叠值守，或提前写明条件、输入身份和预算明确的有效许可。 |
| Goal 执行身份 | 每岗主执行会话默认使用一个夜间 Goal，记录岗位／会话／Goal 身份、计划版本、绑定队列、成功证据、截止时间与停止／恢复条件；启用前先核该客户端可用性，尚未开启须明示。 |
| 独立任务队列 | 每项的 task_id、depends_on、就绪条件、优先级、独立备用项、恢复条件、完成／停止条件。 |
| 写入与执行范围 | 精确写集、只读原件、独占输出目录、允许的工具／机器／版本／次数及单步和总预算、共享消费台账。多个窗口不重复领取额度。 |
| 完整交接单元 | 预先定义的可独立交付物、验收条件、接收岗位、允许解锁的后续任务；不能只写“等另一个人”。 |
| 同步与发布入口 | 远端／分支（默认 origin/develop）、每 30 分钟检查的执行入口、对应 AI／任务身份、每岗唯一发布者、状态／收据／待发送队列的持久保存位置。路径须具体填写，不能只留占位符。 |
| 网络与恢复预算 | 每次 Git 网络操作的有界等待时间、临时故障最多一次重试、后续恢复依据和检查上限；与 EDA 长任务的耗时策略分别设置。 |
| 验收和回执 | 输入／产物 SHA、命令／原始双流／退出码、PASS／FAIL／UNKNOWN、实际 L0–L7、未验项与下一责任人。 |

### 夜间 Goal 模式

三位成员各自在本岗主执行会话中明确开启 Goal，绑定当晚已授权的任务队列、精确写集和验收条件。每岗维持一个主 Goal；完成一个包、切换备用项或每半小时收到更新时沿用该 Goal，不另起一个争写同一目录的执行者。独立子任务仍按原有并发边界执行，不能重复领取发布权或工具额度。

Goal 的目标应写为具体可核验的当晚结果，不只写“持续开发直到天亮”或“完成整个项目”。区分三个状态：当前工具／当前轮结束、一个完整交接单元完成、整份 Goal 达标。完整交接单元达到事前约定条件并通过门禁后即正常发布、留收据，再推进下一项，不等待整个夜间 Goal 完成；仍有必做项或要求远端交付却处于 PUSH_PENDING 时，不把 Goal 标成完成。

Goal 负责跨轮次持续推进，半小时 GitHub 检查仍须有可验证的触发／等待与恢复机制；可由当前执行会话的已验证机制或独立轻量调度器落实。Goal 停止、受阻、用户暂停、客户端退出或额度耗尽后，不能假定仍会准时检查或自动恢复。开夜前验证检查入口与明确 Goal／会话的绑定；不因检查到一次推送就新建或擅自恢复已被用户暂停的 Goal。

缺件时先做授权备用项；全部队列暂不可执行时保存 Goal 身份、队列、缺件、outbox 和恢复条件，不把等待记为目标完成，也不靠重复测试／空转维持活跃。符合既定恢复条件且平台允许续接时，重新核对任务单与权限后继续。截止或额度耗尽时封存已做／未做／待发项并报告，不能以到点代替成功；必要结果已全部满足时可提前完成，不凑时长。

开启／续接 Goal 不增加写权限、工具次数、网络重试、硬件许可或当夜运行时段。Goal 自身的暂停、停止、预算及恢复遵守实际平台规则；无人回复和“需要完成 Goal”都不是授权。真实启用应由各成员在其工作会话执行，修改本规范不等于已替三人启动。

官方产品行为参考：[OpenAI Docs：Goal 的持续目标与完成证据](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)、[长期运行与权限边界](https://learn.chatgpt.com/docs/long-running-work)。本节的每岗一个 Goal、交接单元和等待恢复属于项目执行约定，不是对定时唤醒能力的保证。

先核对 Git HEAD、已知远端提交、已有脏改动／暂存／未跟踪文件、输入身份及已消费额度，缺件记 UNKNOWN／BLOCKED。只拆写集互不重叠且可独立推进的包；主窗口保留集成判断与最后发布。复用已签源码、模型和有效测试，仅验证变化影响范围，不为凑时长重跑、扩充无关工具或恢复旧许可。

开夜前在三台机器的实际 AI／调度器环境分别核验远端读取、认证、所需写权限、脚本路径和工具；人工终端成功不能代替该环境的验证。写入验证只能使用当轮明确授权的发布对象，不额外制造测试提交或测试推送。核清断网、进程退出及机器重启后的恢复入口。若可靠定时入口尚未部署或验证，必须标记 `POLLING_NOT_VERIFIED`，不能把文档要求写成已在后台运行。

## 三、每半小时检查 GitHub

1. **三位成员各自检查**：夜间开工时立即检查；此后每 30 分钟检查一次，不因正在做备用任务而取消。交接单元完成、依赖受阻、准备发布及进程恢复时额外检查。记录时区、检查时间、上次成功时间、远端提交、相关交接和处理结果。错过检查后恢复时立即补查，不伪造遗漏时段的检查记录。
2. 检查由轻量执行入口负责。可先查询指定远端引用，变化后按需 fetch；fetch 成功但无新引用时仍检查本地待处理收件和待恢复任务。无相关变化时不调用模型重读全仓。网络失败记 `REMOTE_STALE` 并保留最后已知状态，不能当作“没有新推送”。
3. **定期检查不自动 pull、rebase、merge、切换分支或修改开发树。**新交付先进入收件队列；在当前工具结束或明确检查点接入。正在运行的仿真／综合／PnR 固定源码与输入 SHA，不中途换文件，也不因轮询到更新而终止正常构建。
4. 检查与 Git 发布使用每岗单一入口和本机互斥，同一仓库的 Git 操作避免并发写引用／索引。已有 AI 写任务运行时只入队；不要每半小时另起一个会修改同一目录的 AI。启动／续接必须绑定明确岗位、任务和会话身份，不能用不确定的“最近会话”。
5. 检查入口与 Goal／AI 当前一轮的状态分别核实：AI 等待或当前轮结束后，已验证的检查入口仍应在约定夜间时段内运行，有可执行交付时按平台规则续接对应 Goal／执行者，不新建重复写入会话，不擅自恢复用户已暂停的目标。单写一句提示词或新建 Markdown 不会完成部署；调度和恢复机制未经演练时如实报告。所有网络调用由执行器落实等待上限，不能只靠提示词承诺取消已挂住的工具调用。

## 四、依赖等待、备用任务与恢复

每次开工、成功检查、收件处理完毕或当前包完成后，按最新有效计划重算任务队列：

1. 前置输入、所需确认和执行许可齐全的任务置 `READY`；按原定优先级取下一项。收到新提交本身不等于前置齐全。
2. 主任务缺件时记 `WAITING_INPUT`，写明缺什么、由谁交付、满足哪一条件恢复；立即转做已授权且不依赖该输入、能缩小当前关键路径缺口的备用任务。备用任务不得抢占更高优先级任务必需的独占资源。
3. 新交付通过核验后，重新判断等待任务；在当前安全检查点保存备用任务进度，再按优先级恢复主任务。不能仅因已进入备用项就忽略上游交付，也不为追新版本反复打断正在运行的工具。
4. 某次工具首失败立即保留原件并说明原因和是否产生修改。临时故障最多重试一次；业务修复、EDA 重跑仍受任务单的工具预算和首失败条件约束，不因本规范扩大。无回复不产生授权，不盲改上游接口、跨写集代做或恢复已消费许可。
5. 无任何 READY／独立备用项时，保存检查点，记 `NO_ACTIONABLE_WORK`、等待条件和下一责任人。结束本轮主动计算，检查入口在当晚约定监测时段内继续运行；明确收工、被用户暂停或时间盒到期后停止。到点不为等队友无限延长；已收到但未处理的交接留给下次恢复。

## 五、交接收据、自动接收与状态

每个完整交接单元保留一份可机读的 JSON 收据及简短说明，包含：

| 字段 | 含义 |
| --- | --- |
| handoff_id、task_id、plan_version | 唯一交接身份、所属任务和计划版本；与 V／D／T 正式编号分开。 |
| producer、consumer | 交付岗位、一个或多个明确接收岗位。 |
| base_commit、result_commit | 完整基线与成果提交 SHA；未提交明确写 null，不填猜测值。 |
| manifest、validation | 原件／依赖／产物路径与 SHA，工具身份、命令、原始双流／退出码、正反结果、首失败、预算消费与实际 L0–L7。 |
| ready_for、next_action、blockers | 可以解锁的具体下游任务、下一动作、已知问题／未验项／仍需许可。 |
| receipts | 接收岗位、观察到的交付提交、接收／验收时间、结果与拒收原因。 |

`result_commit` 指向已经形成的成果提交，收据可在随后提交中引用它；收据所在提交由接收方记录，不把“包含自身完整 SHA”的自引用作为发布条件。原件必须是接收方可获取的仓库内容或当晚已约定的传输位置；只有生产者本机绝对路径、SHA、截图或旧包不能证明交付齐全。

接收方发现发给自己的新收据后自动处理：按 `handoff_id + result_commit + consumer` 持久去重；核计划版本、文件与哈希、依赖／验证结果及写集和许可。过期或被明确替代的交付记录为拒收／已替代；缺件记 `WAITING_INPUT` 并列缺项；齐全则生成 `RECEIVED` 回执并重算 READY 队列。只有完成接收验收并有对应职责时才记 `ACCEPTED`；未经必需的 M2 复核／准入，不开始以其为前置的集成或真实执行。重复检查不重复接入、重跑已签组或消费额度。

交付状态分开记录：`LOCAL_COMMITTED → REMOTE_VERIFIED → RECEIVED → ACCEPTED → INTEGRATED`。未提交保持本地准备状态；多接收方分别记回执。发布者只能核验前两项，不能替接收方签收；实机通过另记，不能由上述状态推定。机器接收／验收回执属于夜间接力的必要回复，可在不夹带未完成成果、遵守发布门禁的前提下发布，不必等待整个上游大任务结项。它不启动额外审核制度，不代替 M2 最终复核，也不要求为每次轮询追加 V／D／T 编号。

收据与回执按生产者／接收者分别写入任务单指定文件，每岗一个写入者，不争写同一汇总表。接收记录本地落盘后才能防重；远端回执未核验时标明待发布，不能把本地回执说成对方已知。中断恢复先读取检查点、去重台账和待发项，再查远端，不从头重做。`当前状态.md`、`任务看板.md` 仍只由 M2 汇总更新。

## 六、发布、推送失败与恢复

1. **每岗一个发布者**收集本岗授权成果，内部其他窗口不同时暂存／提交／推送。沿用三人普通推 `develop`、M2 复核、禁止 force push、逐文件暂存和独立 Git 写调用。发布前检查暂存与待发提交仅含本次授权内容，保留他人修改；`git diff --cached --check` 和 `code/scripts/check_repo.ps1` 全 PASS。最后 fetch 后才取正式编号，编号与功能提交分开。
2. 交付完成先落盘本地提交、收据与**持久待发送队列（outbox）**。每项记目标远端／分支、确切提交／清单、失败原因、命令与退出码、尝试次数、最后核验结果和恢复条件。待发项标 `PUSH_PENDING`；发布过程与开发执行分离，不能让网络命令无限占用主工作，也不能为修复推送重跑同样业务测试。
3. 首次推送／检查失败立即说明原因、是否有本地修改及远端是否已确认。临时传输故障在有界等待后**最多重试一次**，持续失败暂停该发送项并执行独立备用任务。每半小时检查不是无限重复 push 的许可。后续只有任务单预先允许的恢复检查证实连接恢复、远端状态改变或所需权限已获明确批准等新依据时，才重新评估；先核远端，再决定是否发送，并保留原故障和次数。

| 失败类型 | 处理与恢复边界 |
| --- | --- |
| 网络超时／连接拒绝 | 保存原始错误，按临时故障预算处理；仅使用预先验证且允许的连接方式。持续失败保留 outbox。 |
| 认证、仓库／分支写权限、沙盒或审批拒绝 | 停止依赖该权限的操作，报告具体阻断；不换工具、checkout、ACL 或连接方式绕过明确拒绝。已有授权仍有效，但不能代替实际系统权限。 |
| non-fast-forward | 标远端已推进；在安全工作点 fetch，按 Git 规范处理属于本任务的并发变化和编号，重验受影响内容与最终发布门禁，再普通推送，不强推。 |
| 推送超时、结果不明 | 先查询并获取目标远端引用，检查成果提交是否已被远端包含，再决定是否补推；远端无法查询时保留 UNKNOWN。 |
| 门禁、大文件、服务端策略拒绝 | 定位具体原因并停在边界；不跳过门禁、不擅改历史、不自动换交付渠道。 |

远端核验要确认目标成果提交是所观察远端 `develop` 的祖先或与之相同，并核验交付清单。队友已经追加合法提交时，不能只因远端 tip 不等于本地 SHA 就判失败；仅查询远端 tip 也不足以证明祖先关系。fetch 失败或原件不可达时不记 `REMOTE_VERIFIED`。本机发布锁不等于跨电脑锁，仓库中的普通“锁文件”不能保证三机互斥；并发拒绝按上表安全处理。

GitHub 不可达时，本地队列只能保存成果，不能宣称完成跨电脑传输。Git bundle 若用作保底，也须有已约定的真实传输通道；它不含未提交内容，不能替代通信。权限／审批不可达超过五分钟时暂停依赖操作，继续独立工作并报告；超时不是批准，明确拒绝不得绕过。

## 七、收工、验证与最短模板

必要结果齐套即可提前收工，时间盒是上限。收工逐项报告交付身份、实际文件、原始证据、验证等级、首次失败、额度消费、远端核验／接收状态、待发项、未验项和下一责任人。没有收到原件的包保持 PENDING／UNKNOWN；旧失败不回填成功，计划不写成执行结果。次晨 M2 限定复核并汇总状态；待用户决定／转发给真人的事项仍明确标“待用户处理／待转发”，不阻塞已授权的 AI 自动收件。

运行机制正式用于整夜接力前，须在真实两机环境演练正常交付、重复交付、推送失败／结果不明和进程中断恢复，再扩至三机。只完成规范修订时，明确未部署定时器／未验证三机推送，不宣称演练已通过。

```text
# <岗位>：<日期>夜间<目标>（plan_version；最长N小时）
现行任务单／基线／关键路径：...；暂缓项：...
Goal／主会话／岗位身份...；绑定队列／成功证据...；截止与停止／恢复条件...
三岗可用时段／接收与准入安排：...
可用实物／工具／许可证／输入：...；写集／独占输出／次数预算：...
包A：depends_on...；READY条件...；完整交付与验收...；接收方／解锁任务...
包B：独立备用项...；不依赖A的理由...；恢复A的条件...；停止条件...
每30分钟及交接点检查：远端／分支...；执行入口／对应AI身份...；监测起止...
网络单次等待上限...；临时最多一次重试；后续恢复依据与检查上限...
唯一发布者...；收据／回执／去重台账／outbox／检查点实际路径...
主任务受阻→记缺件并做B；新交付→核验／回执／重算READY／安全点恢复。
无可执行项→NO_ACTIONABLE_WORK并保存进度，检查入口监测至约定结束。
晨间回执：文件／提交／原始日志／等级／失败／消费／远端与接收状态／未验／下一责任人。
```

可供三岗各自改写并在工作会话开启的 Goal 模板（须填实际任务、路径、时间与完成条件）：

```text
/goal 按<岗位>的<当夜有效任务单及版本>，在<截止时间>和既有权限／预算内推进<具体必做任务队列>。
以<各项验收证据>核实完成，只修改<精确写集>。完整交接单元完成即按门禁发布、留收据，再做下一项。
每30分钟及交接点检查GitHub，核验新交付并留回执；缺件先做<独立备用项>，条件齐全后在安全点恢复。
推送失败保留提交和outbox，临时最多一次重试，结果不明先核远端；不为网络故障重做成果。
必要任务及规定交付均达标才算完成；暂不可执行时保存等待／恢复条件，不虚报完成。
到截止／预算上限或遇无法解除的边界时如实封存未完成项，不扩大权限、重试或工具额度。
```
