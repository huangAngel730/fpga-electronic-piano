## Codex 本机 Git 写入与沙盒诊断（2026-10-14 实测）

本节记录一次具体故障，不改变上文的分支、编号、门禁和复核规则。M2 的
`C:\Users\Angel17\.codex\worktrees\m2-138k-migration\fpga_gowin`
是 detached HEAD worktree，其 `.git` 指向
`D:\17\project_17\fpga_gowin\.git\worktrees\fpga_gowin3`；共同对象库存于
`D:\17\project_17\fpga_gowin\.git\objects`。正常 Windows ACL 看似允许
Authenticated Users 修改，仍不能代表沙盒内的 Git 进程可写。

- 故障时，`git fetch`／`git merge` 单独调用可以成功；把 `git add`、检查和状态查询
  放在同一个 `pwsh -Command`，用分号或管道串接，会使该复合调用的执行规则解析为
  `unknown`，不命中单条 Git 命令的允许规则，于是留在受限沙盒，报
  `insufficient permission for adding an object ... .git/objects`。
  本次一次带多个文件路径的 `git add -- ...` 也失败；**每次仅指定一个文件路径、
  一条简单 `git add` 调用**，实际上能创建新对象并完成暂存。
- **2026-10-15 C 盘 M2 worktree 实测补充**：对 `code/scripts/check_m2_m1td_physical_20261015.py` 与 `code/scripts/run_m2_m1td_whole_once_20261015.py` 的两次单文件 `git add -- 路径` 在 Codex 工具进程报 `.git/objects` `insufficient permission`，没有完成暂存；用户交互 PowerShell 和随后本工具进程分别以 `git add 路径`（**省略 `--`**）成功暂存，`git status --short`／`git diff --cached --name-only` 核到目标。对不以 `-` 开头的普通仓库相对路径，当前本机优先用**每次一文件、一条独立调用的 `git add 路径`**；路径可能被解释为选项时仍须 `--`。这只记录本机命令形态与结果，**不能断定 `--` 本身造成权限故障**，也不能把命令变形当作绕过明确拒绝授权的方法。失败时保存原命令/错误并核执行规则；不批量 add、不换 checkout、不改 ACL。
- 每个写入动作与每个检查动作分别调用，绝不把它们拼在同一条 shell 命令里：

  ```powershell
  git fetch origin develop
  git add code/docs/任务看板.md
  git diff --cached --name-only
  git diff --cached --check
  git commit -m "docs(register): record validated result"
  ```

  上面是**五次独立调用的示意**，并非可整段粘贴执行的复合脚本。多文件时逐文件
  `git add`，再核暂存区仅包含本次授权文件，保持既有未跟踪文件不动；随后按既有流程
  完成九项门禁、最后 fetch、取号和普通推送。
- `git add --intent-to-add` 对已有跟踪文件返回 0，不证明新 Git 对象可写；
  `git hash-object -w` 若对象已存在也可能返回 0，不能据此宣布 `git add` 已修复。
  本次确认的方法是单文件 `git add` 一个**此前不存在于对象库**的新交付文件，并
  核暂存区只含该文件。探针及 `reset --` 不能代替实际暂存、门禁与远端核验。
- 如 worktree 正在 detached HEAD，不要假装当前是本地 `develop`；先单独 fetch、
  核远端为当前 HEAD 的祖先，门禁和取号合规后才明确 `git push origin HEAD:develop`，
  推送后再 fetch 核 `origin/develop` 与提交 SHA 相同。绝不 `--force`。本次
  T060 原 H 证据提交 `853734b`、V0328 登记 `e0c6af7` 按此流程普通推送并核同。

若**单文件简单 Git 命令**仍失败，保留完整原命令与错误，检查执行规则的实际匹配
结果和进程身份；不要自动重试、改 ACL 掩盖沙盒问题、复制到别的 checkout 或改用
临时 index／其他写入 API 绕过审批。权限不足时如实标记本地待发布。

## 工作流程

1. **开工前先同步**：`git fetch origin`，然后 `git pull --rebase origin develop`。
2. 只修改任务授权范围，见 `三人协作执行手册.md` 第四节与 `code/AGENTS.md` 的写入边界表。
3. **改「接口组」共享文件前先在群里说一句**（共八处、分两组，见下方「推送前检查
   清单」第 3 条；**编号表组不需要提前说明**，D027）。
   **此时不要写编号**——编号留到第 7 步。
4. 小步提交，每次提交保持含义单一，提交信息按下方「提交信息」格式。
5. 运行模块测试并更新文档。
6. 运行 `.\code\scripts\check_repo.ps1`，**必须全 PASS 才能推送**。
7. **最后一步取号（D026）**：`git fetch origin` → `git pull --rebase origin develop` →
   看编号表末尾 → **现在才**写 `V00xx`／`D0xx`／`T0xx` → 做成一个**只含编号**的
   独立小提交。
8. 直接推送：`git push origin develop`。若被拒（远端有未拉取的提交），先
   `git pull --rebase origin develop` 再推，**不要用 `--force`**。
9. M2 复核该次推送的 diff（针对 M1、M3 的改动），一般没问题即通过；M2 自己的改动
   标记「自审」。**发现问题时**由 M2 提出、作者修正，并补一行验证记录。
10. 达到阶段同步点（W4／W6／W8）后由 M2 把 `develop` 合并到 `main` 并打标签。

## 推送前检查清单

分支隔离取消后，这五条是唯一的安全网（D025 §3.3 + D026 + D027）。**缺任一条就不是「直推」
而是「裸推」。**

1. **`.\code\scripts\check_repo.ps1` 全 PASS。** 当前 8／8 项、退出码 0。跑不过不得
   推送——`develop` 必须始终可仿真、可综合。

2. **先 `git fetch`；取号前先看 `develop` 上的最新一行。** 直推后两个人同时取同一个
   `V00xx`／`D0xx`／`T0xx` 是真会发生的。`code/docs/验证记录.md` 的 `V00xx`、
   `code/docs/技术决策记录.md` 的 `D0xx`、`code/docs/任务看板.md` 的 `T0xx`
   **一律从现表末尾取号**，不得预先写死。
   本项目已实际撞号两次——M3 的 `V0031`／`V0032` 与 M1 的 `V0006`／`V0007`，
   最终统一重排为 `V0040`、`V0042`、`V0043`、`V0044`、`V0046`。
   **预分配的旧编号一律作废，直接丢弃。**

3. **共享文件的保护手段分两组（D027），会互相踩的共八处：**

   **接口组（4 个）——改动前必须在群里说一句**

   - `code/rtl/board/electronic_piano_top.sv`（顶层）
   - `code/rtl/common/audio_defs_pkg.sv`（统一演奏事件类型的唯一定义处）
   - `code/constraints/electronic_piano.cst`（引脚约束）
   - `code/docs/模块接口规范.md`（公共接口）

   **编号表组（4 个）——不需要提前说明**

   - `code/docs/验证记录.md`（`V00xx`）
   - `code/docs/技术决策记录.md`（`D0xx`）
   - `code/docs/任务看板.md`（`T0xx` 与状态列）
   - `code/docs/当前状态.md`（全员追加的当前事实）

   编号表组不属于任何一个人的目录，「谁的目录归谁改」对它无效，三个岗位都要往里追加。
   **本项目已发生的两次撞号全部出在这一组**，但撞号的成因是**取号时机**，不是
   「没人知道对方要动这张表」——说一句「我要改 `验证记录.md`」并不传递「我要用哪个号」。
   因此这一组的保护手段是上面第 2 条与下面第 4 条的**取号规则**加 M2 推送后复核，
   而不是改前说明；要求每次推送前先说一句只会变成噪声，反而让接口组那条也被一起跳过。
   清单仍保留八处，是为了让人查得到「这八处是公共文件」（D027）。
   其余按 `code/AGENTS.md` 的写入边界各管各的。公共接口、时钟、复位、采样率、顶层
   端口与引脚仍属受控内容，改动前先按 `变更与决策流程.md` 提变更说明。

4. **编号只在推送前最后一步取（D026）。** 顺序固定为：

   1. `git fetch origin` → `git pull --rebase origin develop`；
   2. 看表末尾，**现在才**确定 `V00xx`／`D0xx`／`T0xx`；
   3. 把编号写进表，做成**一个只含编号与那一行的独立提交**；
   4. 立刻 `git push origin develop`，中间不再夹别的改动。

   **开工时不写编号，干活时不写编号，功能提交里不带编号。** 取号与推送之间不要隔夜，
   窗口越短，撞号概率越低。发现两人取了同一个号时，**以先推送成功的那一行为准**，
   后推者重排自己的编号，旧号作废丢弃；**不要用 `git revert` 回改别人已推的行**。

5. **禁止 `git push --force`。** 需要回退时用 `git revert` 产生新提交。直推时若远端有
   未拉取的提交，`git push` 会被拒——这是 Git 自带的天然保护，**不要去绕过它**。

## 复核要求

- **复核人统一为 M2**（D025）。M1、M3 推送后由 M2 复核该次推送的 diff；**一般没问题
  即通过**，发现问题由 M2 提出、作者修正。
- **M2 自己主责的改动标记为「自审」**，不再要求第二人复核；在任务看板或提交信息中
  注明即可。
- **不强制留痕。** 复核通过时不写验证记录行；**只有发现问题时才补一行**，说明问题与
  处理。原「必须填写合并请求模板全部条目」的要求已取消，
  `.github/PULL_REQUEST_TEMPLATE.md` 不再作为强制门禁（模板保留，可用于较大的改动）。
- 复核人必须实际查看 diff 或运行测试；**不得把未执行的验证阶段写成已通过**。

## 提交信息

提交信息使用 `类型(范围): 摘要` 格式，摘要用中文或英文均可，但同一提交保持一致。

```text
feat(dds): add 32-bit phase accumulator
test(adsr): cover release boundary
fix(i2s): align msb one bclk after lrclk edge
docs(interface): freeze performance event v0.1
```

常用类型：`feat`、`fix`、`test`、`docs`、`build`、`refactor`、`chore`。

- 问题单编号在任务看板中引用，保持一对一或一对多关系清晰。

## AI 参与规则

- AI 只能修改任务单授权的目录，需要跨目录时先停止并列出影响。
- AI 提交前必须运行任务规定的检查（至少 `.\code\scripts\check_repo.ps1`），并给出实际输出。
- AI 不得代替复核人签字，也不得把未执行的验证阶段写成已通过。
- **一个目录同时只允许一名队员及其 AI 修改**（原为「一个分支同时只允许一名队员」；
  按 D025 直推 `develop` 后改为按目录划分，边界见 `code/AGENTS.md` 写入边界表）。
  八处共享文件中，**接口组**改动前先在群里说一句，避免并发重写同一文件；
  **编号表组**不需要提前说明，按「推送前检查清单」第 4 条取号即可（D027）。
  清单见同一条第 3 条。
- **AI 不得在开工时就替主人写好 `V00xx`／`D0xx`／`T0xx`**（D026）。编号一律等到
  推送前最后一步、`git fetch` 之后才取，见「推送前检查清单」第 4 条。
