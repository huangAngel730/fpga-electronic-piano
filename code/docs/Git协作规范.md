## 分支

| 分支 | 用途 | 写入规则 |
|---|---|---|
| `main` | 可演示、可复现的稳定版本 | 只接受来自 `develop` 的合并，禁止直接提交 |
| `develop` | 通过模块测试的集成版本 | 只接受通过复核的功能分支合并 |
| `feature/<name>` | **按人的长期功能分支**，跨任务持续使用 | 仅该岗位本人及其 AI |
| `fix/<name>` | 缺陷修复 | 对应岗位负责人 |
| `docs/<name>` | 仅文档与规范 | 文档发起人 |

**按人分支，不按任务分支（2026-09-15 明确）。** 不再为每个任务单独创建分支；每个岗位维护自己的长期功能分支，任务完成后按需合并进 `develop`。分支名中的 `<name>` 描述该岗位的长期负责方向，不是单个任务。**新增长期分支前先在本节登记**——此前 `任务看板.md` 的分支列写了 30 个分支名，而远端实际只有 10 个，其余 22 个从未创建。

## 工作流程

1. 在本人长期功能分支上工作；**每次开工前先按下方「分支同步规则」同步 `develop`**。
2. 只修改任务授权范围，见 `三人协作执行手册.md` 第四节。
3. 小步提交，每次提交保持含义单一。
4. 运行模块测试并更新文档。
5. 推送分支并创建合并请求，使用 `.github/PULL_REQUEST_TEMPLATE.md` 模板。
6. 由至少一名非作者复核。
7. 合并到 `develop` 后运行全回归。
8. 达到阶段同步点后由 M2 合并到 `main` 并打标签。

## 分支同步规则

按人长期分支会长期存在，各分支之间会持续拉开。以下三条是**必需**的配套规则（2026-09-15 增补），缺任一条就会出现编号冲突与合并困难：

1. **落后上限 10 个提交。** 长期分支相对 `develop` 的落后提交数**不得超过 10**；超过即先同步、再开工。（**只读存档分支不受此限**，见本节末尾「例外」。）

2. **开工三步。** 每次开始改文件之前，按顺序执行：

   ```text
   git fetch origin
   git rev-list --left-right --count origin/develop...HEAD   # 左为落后数，右为领先数
   git rebase origin/develop                                 # 落后就同步
   ```

   落后数超过 10 时不得开工。

3. **编号不在分支上分配。** `code/docs/验证记录.md` 的 `V00xx` 与 `code/docs/技术决策记录.md` 的 `D0xx`，**由把该分支合并进 `develop` 的人从现表末尾取号**，不得在分支上预先写死。

   理由：各人在自己分支上独立取号，合并时必然撞号。**本项目已实际发生两次**——M3 的 `V0031`／`V0032` 与 M1 的 `V0006`／`V0007` 均与 `develop` 已占用编号冲突，最终统一重排为 `V0040`、`V0042`、`V0043`、`V0044`、`V0046`。**分支上预分配的旧编号一律作废，直接丢弃。**

**例外：跨目录重命名的老分支不要直接 rebase。** 2026-09 期间顶层目录由 `代码/`、`准备/` 改为 `code/`、`prep/`，并删除了 `legacy-prototype/`。跨这次重命名的分支（如 `feature/input`、`feature/model-dds`）若直接 `git rebase develop`，Git 会把 `代码/...` 与 `code/...` 当作两套不同文件，产生大量**假冲突**，无法区分哪些是真实改动。此类分支视为只读存档，改从 `develop` 新建分支，原成果按迁移流程并入 `develop`。

目前属于此类的有 **`feature/input`**（M3，落后 26／领先 3）与
**`feature/model-dds`**（M1，落后 48／领先 1），两者的独有提交成果**均已迁入
`develop`**（分别见 `b0d6479` 与 `eb82185`），文件级已无独有内容。

**新建活分支时不要复用这两个名字**——名字被存档占用后再用于新分支，会让「只读」这条
约束失效，也无法再用分支名判断该分支能不能 rebase。

## 合并请求要求

合并请求必须填写模板中的全部条目，至少有变更摘要、运行命令、PASS 结果、验证等级、未验证的硬件项目，以及是否影响公共接口和约束。

复核结论使用通过、有条件通过或退回，并列出依据。复核人必须实际运行测试或查看报告。

## 提交信息

提交信息使用 `类型(范围): 摘要` 格式，摘要用中文或英文均可，但同一提交保持一致。

```text
feat(dds): add 32-bit phase accumulator
test(adsr): cover release boundary
fix(i2s): align msb one bclk after lrclk edge
docs(interface): freeze performance event v0.1
```

常用类型：`feat`、`fix`、`test`、`docs`、`build`、`refactor`、`chore`。

## 问题单

- 任务拆解和排期使用 `.github/ISSUE_TEMPLATE/task.yml`。
- 缺陷和异常使用 `.github/ISSUE_TEMPLATE/bug.yml`。
- 问题单编号在任务看板中引用，保持一对一或一对多关系清晰。

## 持续集成

`.github/workflows/rtl-smoke.yml` 在推送和合并请求时执行：

- 对 `prep/脚本/` 下的 Python 生成脚本做语法检查。

**该工作流目前不构建 `code/rtl`。** 它原先还有一个"用 Icarus 编译并运行原型自检 testbench"的 job，2026-09-15 随 `legacy-prototype/` 归档一起删除：那 4 个源文件构成闭包（无 `include`、无 `readmem`），对 `code/` 下任何改动都不可能产生结果差异，等于给提交一个必然为 PASS 的绿灯。给它补一个真正编译 `code/rtl` 与 `code/tb` 的 job 是待办事项，见 `code/docs/验证记录.md` V0041。

因此当前的合并门禁实际由本地 `code/scripts/check_repo.ps1` 承担，而不是持续集成。持续集成与本地检查都只能证明 L1 至 L2 级别，不能代替上板验证；综合、布局布线与时序（L4/L5）需要 Gowin EDA 和器件库，无法在 GitHub runner 上运行。

## 禁止提交的内容

- `.tools/` 目录和任何安装包。
- 波形文件、仿真数据库和临时缓存。
- 比特流、码流和厂商工程自动生成目录。
- 无必要的大型二进制文件。

具体忽略规则见根目录 `.gitignore`。新增例外时先在合并请求中说明理由。

## AI 参与规则

- AI 只能修改任务单授权的目录，需要跨目录时先停止并列出影响。
- AI 提交前必须运行任务规定的检查，并在合并请求中给出实际输出。
- AI 不得代替复核人签字，也不得把未执行的验证阶段写成已通过。
- 一个分支同时只允许一名队员及其 AI 修改，避免并发重写同一文件。
