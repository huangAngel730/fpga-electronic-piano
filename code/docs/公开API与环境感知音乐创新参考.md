# 公开 API 与环境感知音乐创新参考

更新时间：2026-09-25。

## 一 文档定位

本文记录高云选题二“基于 FPGA 的实时多音色合成电子乐器引擎”的候选创新方向，供后续方案评审、任务拆分和答辩材料选用。

- 本文是**创新角度参考**，不是赛题原文、冻结需求或已经完成的功能。
- 公开 API 只作为外部低速控制数据源，不能替代 FPGA 的逐样本、逐声部实时音频合成。
- 是否实施必须服从当前关键路径：基础要求、核心吞吐量、三维表情、效果器、低延迟和现场自证优先。
- 若实施需要增加公共事件字段、寄存器、顶层端口或通信协议，必须先按 `code/docs/变更与决策流程.md` 提交影响分析。

## 二 public-apis 的正确定位

`public-apis/public-apis` 是公开 API 的分类目录，记录候选服务的简介、认证方式、HTTPS 和 CORS 等信息；它本身不是统一的数据服务器。真正的数据由目录中链接的第三方服务提供，接口、额度、认证和服务条款都可能变化。

本项目只把该目录用作“API 黄页”和前期调研入口，不把它作为运行时依赖。选定具体服务前，必须重新核对：免费或竞赛用途许可、API Key、HTTPS、请求配额、超时、地区可用性、字段单位、异常值和断网降级方案。

外部参考：`https://github.com/public-apis/public-apis`，访问日期 2026-09-25。

## 三 创新价值排序

| 层级 | 建议定位 | 代表内容 | 价值判断 |
|---|---|---|---|
| 核心技术创新 | 主创新 | FPGA 高吞吐量多声部架构、定点流水线、声部分配、低延迟、硬件效果器 | 最能说明为什么使用 FPGA，优先级最高 |
| 演奏交互创新 | 重要辅助创新 | Velocity、Pitch Bend、Modulation、Sustain 与音色/效果器的独立映射 | 与赛题拓展要求直接相关，需实物抓包和可听效果证明 |
| 应用场景创新 | 差异化亮点 | 天气、空气质量、昼夜等环境数据驱动音乐场景 | 易形成展示记忆点，但不能替代核心指标 |

开发投入建议为 FPGA 核心与验证约 70%～80%、交互与显示约 15%～20%、联网或公开 API 创意约 5%～10%。这只是项目投入建议，**不是官方评分比例**。

## 四 推荐主题：环境感知生成式电子乐器

优先考虑天气、空气质量、风速、湿度、昼夜和日照等更新缓慢的数据。它们适合控制“音乐场景”，而用户的琴键和表情控制继续负责实时演奏。

建议的作品表述：

> 面向环境感知生成式演奏的 FPGA 实时多音色合成引擎。外部环境数据负责低速调制音阶、音色和效果器场景，演奏者通过多维 MIDI 表情进行实时控制，所有正式音频样本均由 FPGA 硬件逐样本生成。

## 五 建议系统架构

```text
第三方公开 API 或本地 Mock 数据
              │ HTTPS / JSON
              ▼
Raspberry Pi 或 PC 上位机
请求、缓存、字段校验、归一化、场景映射
              │ UART / SPI / USB 串行链路
              ▼
FPGA 控制入口
命令校验、影子寄存器、参数限幅、平滑更新、CDC
              │
              ▼
FPGA 实时音频链路
DDS/多音色 → ADSR → 混音 → 效果器 → PT8211
```

- Raspberry Pi 或 PC：TLS、HTTP、JSON、API Key、重试、缓存和单位转换；
- FPGA：演奏事件处理、逐样本合成、参数平滑、混音、效果器和音频输出；
- STM32 如后续需要，可承担面板和通信桥接，但不替代 FPGA 合成核心；
- 不建议在 FPGA 中直接实现完整 TCP/IP、TLS、HTTP 和 JSON 解析。

## 六 数据到音乐参数的候选映射

| 外部数据 | FPGA 内候选目标 | 更新与保护 |
|---|---|---|
| 温度 | 滤波器截止频率、音色亮度 | 合理区间限幅，1～5 s 平滑 |
| 相对湿度 | 延迟反馈、混响湿声比例 | 映射至 0～1，对反馈量设置上限 |
| 风速 | LFO 频率、颤音深度 | 限制最大调制深度，避免明显跑调 |
| 天气类别 | 音色场景、音阶或和弦色彩 | 场景切换使用交叉淡化或参数斜坡 |
| 空气质量 | 噪声比例、失谐、滤波器共振 | 只作艺术映射，不宣称科学因果 |
| 昼夜/日照 | 明暗音色、包络长度、空间效果 | 可由本地时间作离线替代 |

API 原始值不能直接写入音频寄存器，必须先校验、限幅和归一化。所有影响音频连续性的参数采用斜坡、插值或块边界提交。同一组 Mock 数据必须产生确定且可复现的参数。

## 七 候选控制字段

以下字段只用于讨论数据模型，不代表公共接口已经冻结：

| 字段 | 建议类型 | 说明 |
|---|---|---|
| `environment_scene_id` | 无符号枚举 | 晴、雨、风、夜间等场景编号 |
| `environment_intensity` | Q1.15 | 场景总体强度 |
| `timbre_brightness` | Q1.15 | 音色亮度或滤波器控制量 |
| `modulation_depth` | Q1.15 | 环境附加调制深度 |
| `effect_mix` | Q1.15 | 延迟/混响湿声比例 |
| `data_age_s` | 无符号整数 | 最近有效数据的新鲜度 |
| `source_status` | 位域 | 在线、缓存、Mock、超时、字段异常 |

上位机向 FPGA 发送时建议采用带版本号、序号、长度和 CRC 的小型二进制帧，而不是把 JSON 原文送入 FPGA。正式协议应复用或扩展既有控制通道。

## 八 最小可行版本

1. 在 `code/software/` 下建立独立网关程序，先读取晴天、雨天、强风三组本地 Mock JSON；
2. 建立纯软件参数映射与单元测试，覆盖边界值、空字段、错误类型和过期数据；
3. 通过现有通信通道发送归一化参数，先只控制一个参数，例如音色亮度；
4. FPGA 端加入影子寄存器、限幅和参数平滑，并用 testbench 检查突变输入；
5. 上板验证 Mock 场景的可听差异和无爆音切换；
6. 最后再替换为实际 API，并保留 `--offline` 或“一键 Mock”模式。

现场演示以本地 Mock/缓存为主、在线数据为可选增强，避免网络、DNS、配额或第三方服务异常影响核心演奏。

## 九 验证与答辩证据

| 验证阶段 | 证据 |
|---|---|
| 软件参考 | 固定 JSON 输入对应固定归一化参数，边界和异常用例自动 PASS |
| RTL 仿真 | 控制帧校验、CDC、参数限幅和平滑更新自动 PASS |
| 子系统联调 | 同一 Mock 场景可重复得到相同 FPGA 状态和可听变化 |
| 上板实测 | UART/SPI 帧、状态寄存器、错误计数器和音频输出同步观测 |
| 答辩演示 | 原始数据 → 映射参数 → FPGA 状态 → 波形/频谱/听感的完整链路 |

推荐答辩表述：

> 设计了一套可离线复现的环境感知控制链路，将非实时外部数据转换为有边界、可平滑更新的定点场景参数，并由 FPGA 完成确定性低延迟的多声部逐样本合成。

## 十 风险和止损条件

- 若 32 路目标、三维表情、效果器和低延迟证据尚未完成，不优先投入联网功能；
- 必须保留 Mock 和最近一次有效缓存，超时后保持当前场景或平滑回到默认值；
- API Key 只保存在环境变量或忽略提交的本地配置中；
- 通过适配层隔离供应商字段，避免绑定某一家服务；
- 报告、视频和现场验收使用固定 Mock 数据作为可复现基准；
- 使用地理位置数据时，不得暴露学校名称、Logo 或精确校园位置；
- 若需要大规模修改公共接口或影响 W3～W6 关键路径，暂停实施，只保留本文作为答辩储备方向。

## 十一 当前建议

当前只保留本方向为候选创新，不立即进入 RTL 开发。正式立项门槛建议为：

1. 4 复音基础链路和核心音频模块稳定；
2. 32 路档位或等效吞吐量路线已有资源与时序依据；
3. Velocity、Pitch Bend、Modulation 的实物链路已验证；
4. 至少一种 FPGA 效果器和端到端延迟测量已形成证据；
5. 团队仍有独立人员和时间完成上位机、协议与离线演示。

满足门槛后，再从天气/空气质量方向建立单独任务；否则本文仅用于报告中的“可扩展性与后续工作”章节。
