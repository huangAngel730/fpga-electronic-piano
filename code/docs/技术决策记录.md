## D015 振荡器统计口径与合成路线得分效率

- 日期：2026-09-12
- 提议人：M2，依据赛题原文《核心评分规则与现场验证标准》第 1 条
- 状态：提议
- 问题：赛题对"独立发声单元"给出了明确定义和分路线统计规则，但项目在冻结 D004（DDS 加单周期波表）时没有引用该规则，也没有论证不同合成路线的得分效率。这会影响波表容量、复音档位、资源预算（T016）和报告口径。
- 赛题原文规则：
  - 独立发声单元为包含**独立相位累加器、频率调控、包络控制**的完整振荡器。
  - **单波表采样查表不计多谐波数量，仅计单个振荡器。**
  - 加法合成按运算分量统计。
  - FM 按调制运算器统计。
  - 物理建模按并行弦或模态单元统计。
- 对本项目的直接影响：当前 D004 路线下，一个声部即使波表内含 2048 个谐波，也**只计 1 个振荡器**。若改用加法合成，每个正弦分量独立计数。两条路线的"每单位逻辑资源可申报的振荡器数"并不相同。
- 候选方案：
  1. 维持 D004 波表路线，依靠声部数堆到 32。资源效率高，复音容易做多，但每个声部只计 1。
  2. 改为加法合成，用分量数申报。可申报数量大，但每分量需独立相位累加器和运算单元，资源开销显著上升。
  3. 混合路线：基础声部用波表保证复音数，另设一组加法合成分量或 FM 运算器作为规模补充。
- 决策：**暂不改变 D004**，先按方案 1 推进保底档。同时要求 M1 与 M2 在 T016 资源预算中，按本条的三种统计口径分别测算可申报振荡器数，作为加分档（G6）路线选择的依据。
- 依据：保底档需要确定的交付，不宜在 W2 就切换架构；但统计口径必须提前落到文档，否则 T016、T033 和报告会各自使用不同口径，导致对外数字不可复现。
- 影响模块：`项目事实与范围.md` 的规模表述、`资源预算与复音规划.md`、T016、T033、报告第三章与第四章、答辩材料。
- 回退方案：若 T016 测算显示波表路线在 32 声部下达不到资源与时序要求，再按方案 3 引入混合路线，由 M2 发布接口影响分析。
- 待办：M1 与 M2 在 T016 中给出三种口径的测算表；三人确认后本决策改为已冻结。

## D016 系统吞吐量指标作为核心 KPI

- 日期：2026-09-12
- 提议人：M2，依据赛题原文《核心评分规则与现场验证标准》第 2 条
- 状态：已冻结
- 问题：赛题把系统吞吐量列为核心评分依据，但项目此前从未在文档中记录该指标，导致指标表述分散、无法指导优化方向，报告也缺少统一口径。
- 赛题原文：以「**同时活跃可闻独立振荡器总数 × 实际音频输出采样率**」为核心评分依据，**过采样不叠加加分**。
- 决策：把该公式确立为项目的**第一核心 KPI**，在所有对外材料中统一使用。
  - 记法：`吞吐量 = 同时活跃可闻独立振荡器总数 × 实际音频输出采样率`，单位「振荡器·采样/秒」。
  - 振荡器计数口径严格遵循 D015。
  - "实际音频输出采样率"指 I2S 实际输出的采样率，不是内部过采样率。过采样不参与计算。
  - 保底档目标：4 振荡器 × 48 kHz = **192 K 振荡器·采样/秒**。
  - 加分档目标：32 振荡器 × 48 kHz = **1.536 M 振荡器·采样/秒**。
  - 该数值必须区分"目标值"与"实测值"，实测值只有在 T016 资源报告和时序收敛报告出具后才能写入正式材料。
- 依据：核心评分依据必须在最早阶段进入设计约束，否则优化方向可能偏离评分重点。过采样不计入的规则同时说明，单纯提高内部运算速率不能提升该项得分。
- 影响模块：`项目事实与范围.md`、`资源预算与复音规划.md`、T016、T029、T033、T034、报告第四章与第六章、答辩材料。
- 与采样率的关系：在振荡器数不变时提高采样率同样能提升该指标。但采样率受 I2S 格式、DAC 能力和板载音频链路限制，且接口 v1.0 已冻结 48 kHz。提高采样率属于接口变更，必须走 `变更与决策流程.md`，不得由单个任务私自调整。
- 回退方案：若实测吞吐量与目标差距过大，按 D012 两阶段范围把对外口径降为实测值，并把目标值移入展望部分。

## D017 I2S 数据相位由标准 I2S 修正为 LSBJ

- 日期：2026-09-12
- 提议人：M2
- 状态：已冻结
- 问题：D013 发布的 `模块接口规范.md` v1.0 第五节把数据相位固定为
  "LRCLK 翻转后延迟 1 个 BCLK 输出 MSB"，即**标准 I2S（Philips 格式）**。
  但板载 DAC 为 **PT8211**，其数据格式是 **LSBJ（LSB 对齐 / 日本格式）**。
  两者的数据在帧内**相差 15 个 BCLK**。若按 v1.0 实现发送器，
  每个样点都会被错位锁存，**输出为噪声而非音频**。
- 候选方案：
  1. 修订接口规范为 LSBJ，发布 v1.1。
  2. 保留标准 I2S，在 DAC 前增加一个格式转换级。
  3. 不改规范，在板级另加一颗支持标准 I2S 的 DAC。
- 依据（数据来自 `code/docs/PT8211_V1.7_E_数据手册.pdf`）：
  - 手册 DESCRIPTION 原文为 "digital input timing format is Least
    Significant Bit Justified (LSBJ), or so called Japanese input
    format"；正文描述为 "When the Word Select (WS) clock in the Low
    level, the DIN data will be shifted to the right input register"，
    即 **LSB 紧贴 WS 跳变沿**。
  - 时序余量核算：Fbck 3.072 MHz 对上限 18.4 MHz（余量 5.99×）、
    Fws 48 kHz 对上限 384 kHz（余量 8.0×）、tH 实际 162.8 ns 对
    下限 25 ns（余量 6.51×）、VIH 3.3 V 对下限 1.8 V。**全部满足**。
  - **关键判断**：该行描述的"数据相位"约束的是 **FPGA 引脚上的串行波形**，
    其唯一消费者是板载 PT8211。模块之间传递的是**并行** `pcm_left` /
    `pcm_right`（见 `模块接口规范.md` v1.0 第 293 行）。项目不存在第二个
    I2S 设备。因此该行属于**板级输出格式**而非模块间接口，
    按事实修正即可，不构成接口语义变更。
  - 方案 2 的代价：多 1 个 RTL 模块与 testbench，额外延迟 **20.8 μs**

## D025 取消按人长期分支：一律直推 develop，复核归口 M2，main 只在阶段同步点使用

- 日期：2026-09-16
- 提议人：M2（依据用户裁定）
- 状态：已冻结

### 问题

`Git协作规范.md` 原定「按人长期分支 + 功能分支合并进 `develop` + 至少一名非作者复核」。
V0051 的实测结果是：

- 远端 10 条分支（含 `main`、`develop`）里，8 条非 `develop` 分支中有
  **5 条从建立至 2026-09-16 从未被使用**（`feature/board`、`feature/i2s` 与三条 `docs/*`），
  另 1 条已全部并入、2 条转为只读存档；
- `feature/input`、`feature/model-dds` 的最后归宿都是「成果迁进 `develop` 后转只读存档」；
- 自 `eb82185`（2026-09-15）之后的**全部 7 个提交都直接落在 `develop` 上**，
  没有功能分支、没有合并请求、没有非作者复核；
- 分支机制在本项目唯一可确认的产出是**两次编号撞号**（M3 的 `V0031`／`V0032`、
  M1 的 `V0006`／`V0007`）。

即：**约定与实际长期不一致，而实际做法没有造成事故。**

### 候选方案

1. 恢复按人长期分支，严格执行合并请求与非作者复核。
2. 保留分支，但把复核简化为「M2 在合并时复核」。
3. **取消按人分支，一律直推 `develop`；复核归口 M2；`main` 只在阶段同步点使用。**

### 决策

采用**方案 3**。用户 2026-09-16 裁定：「复核不用搞那么麻烦，一般没问题，要不全部
变成 M2 在合并分支时复核」，并在三项确认中选定「全部 M2 复核，M2 自己的标自审」
「平时不留痕，只在发现问题时写」「就按这个做，`main` 也一起修」。

**3.1 分支**

- **不再新建按人功能分支。** 三人一律在 `develop` 上工作并直接推送。
- 远端现存 8 条非 `develop` 分支（2 条只读存档 + 1 条已并入 + 5 条引导期空壳）
  一律视为历史，**不再使用，也不再新建同名分支**。是否删除留待三人同步会。
- **`main` 保留但改变用法**：只在**阶段同步点（W4／W6／W8）由 M2 把 `develop`
  合并进 `main` 并打标签**（形如 `v0.4-w4`）。`main` 语义仍是「可演示、可复现的
  稳定版本」，供答辩、录像与对外演示使用；日常开发不碰它。
- **D014（引导期直推例外）的结论被本决策吸收**：直推不再是「例外」而是默认做法。
  D014 正文按「只追加不改写」保持原样，其「该例外在开启分支保护后失效」一句随之
  作废——因为不再需要功能分支保护。

**3.2 复核**

- **复核人统一为 M2。** M1、M3 推送后，**M2 复核该次推送的 diff**；一般没问题即通过，
  发现问题由 M2 提出、作者修正。（原先写作「合并时」，因不再有合并动作，时点落到
  推送动作本身。）
- **M2 自己主责的改动标记为「自审」**，不再要求第二人复核；在任务看板或提交信息中
  注明即可。
- **不强制留痕。** 复核通过时不写验证记录行；**只有发现问题时才补一行**说明问题与
  处理。原「必须填写合并请求模板全部条目」的要求取消。
- `code/AGENTS.md` 写入边界表的复核人列与 `任务看板.md` 的复核人列，同步改为按此
  口径填写（`任务看板.md` 的「复核人」列现只有 `M2` 与 `自审` 两个取值）。

**3.3 替代保障（分支隔离取消后必须守的四条）**

1. **推送前必须运行 `.\code\scripts\check_repo.ps1` 并全 PASS**（当前 8／8、退出码 0）。
   跑不过不得推送。`develop` 必须始终可仿真、可综合。
2. **推送前先 `git fetch`；取号前先看 `develop` 上的最新一行。** 直推后两人同时取
   同一个 `V00xx`／`D0xx` 是真会发生的；编号仍按「从现表末尾取」的规则决定。
3. **共享文件改动前先在群里说一句。** 会互相踩的只有四处：
   `code/rtl/board/electronic_piano_top.sv`、`code/rtl/common/audio_defs_pkg.sv`、
   `code/constraints/electronic_piano.cst`、`code/docs/模块接口规范.md`。
   其余按 `code/AGENTS.md` 的写入边界各管各的。公共接口、时钟、复位、采样率、顶层
   端口与引脚仍属受控内容，改动前先提变更说明（`变更与决策流程.md` 不变）。
4. **禁止 `git push --force`。** 需要回退一律用 `git revert` 产生新提交。直推时若远端
   有未拉取的提交，`git push` 会被拒——这是天然保护，不要绕过它。

  `每周同步记录.md`、`验证记录.md` 历史行、`技术决策记录.md` D001–D024 正文。
- **不作废**：`code/docs/变更与决策流程.md` 的受控内容变更说明要求；

### 理由

1. 分支在本项目的实际作用接近零，而维护成本已经真实造成两次编号撞号事故。
2. 项目规模小、周期八周、写入边界按目录切分，三人本来不碰同一批文件；真正会冲突的
   只有四处共享文件，用「改前说一句」比分支隔离更省。
3. 直推有 Git 自身的非快进保护兜底，不可能悄悄覆盖队友提交。
4. 复核归口 M2 与「M2 是集成负责人」的既有定位一致，同时修掉了「规则写着要复核、
   实际没人复核」的空转。

### 已知风险与接受理由

- **`develop` 一旦被推坏，三个人都被挡住**（分支模式下只坏一个分支）。接受理由：
  `main` 保留为阶段点的稳定版本，且每次推送前必须跑 `check_repo.ps1`；回退用
  `git revert`，成本是分钟级。
- **M2 自己的改动无人复核**（顶层、约束、构建入口）。接受理由：用户明确选定此口径；
  `main` 阶段标签与 `check_repo.ps1` 提供兜底。
