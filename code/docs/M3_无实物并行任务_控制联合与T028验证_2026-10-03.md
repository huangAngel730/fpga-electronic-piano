## A：最新输入到四槽FCW联合验收（先做、无外部依赖）

现有检查分别覆盖parser→snapshot与snapshot→FCW；本任务的新增价值是一次实际串联：

`最新midi_input/uart_rx或midi_event_parser → performance_event_fifo(32) → performance_control_snapshot → pitch_mod_snapshot_pipeline(四路)`。

主压力TB可以字节输入；另给少量真实50MHz/31250 UART混合序列验证字节入口没有被跳过。
独立记分板只在公共FIFO输出成功握手时更新256个source/channel控制状态；事件尚未被接受时不能提前应用。
Program Change按原0～127离散事件核对，不擅自映射音色，也不修改Pitch/Mod状态；Note/CC64/Program必须保持各输入流离散顺序。
连续控制会合并并可跨离散事件重排，不能用错误的“所有消息到达顺序完全不变”参考判定。

### 身份与base FCW输入合同

本任务不例化正式router/ADSR/DDS，也不伪称完成整机。
四槽occupied/source/channel/generation与base FCW由**明确标为TB声部夹具**的驱动提供。
控制快照请求在E成功接受时，同时冻结四路base FCW；直到对应snapshot被四槽FCW消费者握手前保持该base不变。
request的live槽/base在E后可以改变，已冻结事务结果必须仍绑定旧请求。不得直接把变化的live base拼入旧snapshot。
现有snapshot模块没有base端口，夹具冻结连接逻辑只属于TB；若正式接入需要接口变更，由M2另行处理。
NoteOn脉冲不能从持续valid生成，按已有M1单拍合同驱动：同拍与异拍场景都要覆盖。

### 必测场景

1. 最新A/B解析器的Note、CC64、Program与Pitch/CC1混合流经过公共FIFO实际握手。
2. 公共FIFO满载及同拍出入、另一source竞争、快照读取4拍反压；后级ready多拍拉低时完整payload稳定。
3. control事件与采样请求同拍：按现有write-through合同快照包含新值；未握手的控制不生效。
4. 所有256身份的隔离，四槽同/不同通道，空槽默认值；至少512个成功消费请求、128个非零控制结果，避免只跑旁路。
5. 48kHz请求1041/1042拍，参数快照只接受一次；LFO每个occupied槽每次真实计算只推进一次。
6. 快照产生后live身份/base变化、模拟抢占/代次切换、取消在途/held结果、复位各阶段，旧tag不能作为新请求结果接收。
7. 中心/Mod0/range0口径须按实际模型：**Mod非零时bend=0或range=0仍可有颤音**，不能依据旧文档的不完整旁路表判错；默认5Hz/±50音分按候选参数实测，不宣称用户最终冻结。
8. 真实UART小组至少覆盖Pitch、CC1、Program、Note/CC64组合；不使用人为覆盖parser内部状态代替输入。

结果FCW必须由独立状态记分板 + 已签收M1纯Python PitchModVoice按接受请求逐样本生成，不拿第二份同实现RTL作为唯一oracle。
可观察层级LFO相位作为附加诊断，主体断言仍从输出请求id、来源、通道、generation、occupied与FCW验证。
只把TB纯访问函数作为Icarus兼容方式，不改DUT；ModelSim也可用，但必须日志与退出双重确认。

三个行为反例须先编译成功再由断言拒绝：snapshot保持valid重复推进LFO、使用live base代替冻结base、破坏请求id/generation。
不重新运行旧62279向量全网格或数学误差扫描来凑数量；本任务补联合边界。

交付：TB、Python逐样本记分/runner、固定seed与场景manifest、README；失败非零退出，缺ROM/空capture/超时必须拒绝。
