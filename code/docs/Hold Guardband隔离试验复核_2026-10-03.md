# Hold Guardband隔离试验复核（2026-10-03）

## 结论

本轮仅在V0158按键计数末端选择候选的冻结音画组合上进行一次Gowin PnR，实验副本把系统域Hold不确定度从`0.500 ns`加严到`0.550 ns`。**实验通过预设筛选条件，但不直接替换当前正式基线，也不生成/烧录生产码流。**

上一版正式候选仍是 `code/output/button_counter_tail_select_20261003/B_tail_select`；本轮候选只作为后续最终组合STA的布线参考。

## 固定范围

- 器件：GW5AT-LV60PG484AC1/I0，Gowin V1.9.11.03 Education。
- 固定V0158 B候选44个工程输入、ROM、CST、RTL、PnR选项和自动Hold修复 `-correct_hold 1`。
- 文件列表只有一个差异：SDC中系统域Hold uncertainty `0.500 → 0.550 ns`。
- 没有修改正式RTL、公共接口、时钟、引脚或M3输入模块；没有进行seed搜索，没有烧录。

工具手册定义`set_clock_uncertainty -hold`同时作用于Hold和Removal，因此本轮同时检查这两类结果。手册也说明Gowin的标准Tcl流程是`run syn`、`run pnr`或`run all`；没有使用未确认的独立“只重跑STA”命令。

两个版本所有时钟域的Setup/Hold负Slack端点数均为0，TNS均为0；最小脉宽最小Slack为+2.327 ns，未变差。

实验版本的最差系统Hold路径从原来的UART计数器自保持路径换成按键去抖计数器路径，说明加严约束推动了重新布线，但没有消除“最短路径贴边”这一整体特征。

## 关于+0.051 ns

实验工具在0.550 ns约束下对同一实验布线报告+0.001 ns。对于保持不变的同一条系统同步路径，把约束回代到项目原始0.500 ns，得到约`+0.051 ns`；考虑报告显示精度，保守下界为`+0.0505 ns`。

这个数是**同一布线、改变Hold不确定度后的约束回代值**，不是第二次用0.500 ns重新PnR/STA得到的独立工具Slack。报告没有修改原始HTML，也没有把回代值冒充正式STA结果。

## 性价比判定

预设筛选条件全部满足：

- 原条件回代的系统Hold保守下界≥+0.050 ns；
- 系统Setup≥+0.500 ns；
- 所有时钟域无Setup/Hold违例；
- Recovery、Removal和最小脉宽均为正；
- Logic、Register、DSP、BSRAM没有增加；
- RTL、容量、握手和延迟没有改变。

因此，**Hold加严试验本身是成功的，副作用很小，值得保留为后续最终组合的布线候选。** 当前不把它直接提升为正式稳定版本，因为它只覆盖V0158冻结组合，没有包含最新MIDI parser、Pitch/Mod、T028效果器和后续音频接入；这些功能接入后必须重新做最终整机PnR/STA。

## 后续决定

1. 正式基线暂时保留V0158上一版，不回滚、不改生产RTL、不烧录。
2. 后续最终组合构建时，优先复用本轮“系统Hold加严到0.550 ns”的约束策略，再以最终完整源码做一次统一PnR/STA。
3. 最终组合如果在0.550 ns条件下仍无违例、Setup和Removal满足门槛，才决定是否采用对应布线和正式约束；若最终功能加入后余量恶化，保留原正式版本并针对新的最差路径处理。
4. 不再针对当前冻结组合重复换写法或搜索seed。
