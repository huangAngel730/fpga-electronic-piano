# T058最新整机时序不足：根因分类与修复顺序

2026-10-09，用户要求分析。本轮只核既有报告/源码、给修复方案，不修改RTL/SDC/CST/GSC、不启动新的综合/PnR/仿真/下载。对象为2026-10-08执行的retained_payload_v2唯一run，工具完成全部流程但发布门禁失败，不能引用旧L的L5结论。HDL依据源码分析，不是CodeGraph索引。

## 结论

当前40MHz普通数据Setup并未失败。实际障碍分为：四条新观察复位同步器输入Recovery检查；一条原音频同域数据Hold；另有资源profile与实际RAM映射不一致，后者不是时序失败。

普通Setup+1.846ns，新payload最差+8.500ns/56存活位，三新同步器二段均非负。Hold−0.011ns，Recovery−3.738/−1.309ns，Removal+0.002ns。工具summary Setup violated4对应四条Recovery，不应描述成四条音频运算Setup负路径。Fmax43.189/31.953/1101.928MHz只反映相应max-delay口径，不证明Hold/Recovery通过。

## 1. Recovery：先判异步复位入口，再决定拓扑或物理修复

真实pixel→audio两路径：u_event_bridge/u_video_reset/sync_chain_1_s0/Q至u_wave_bridge/u_mailbox/u_src_reset/sync_chain_0/1_s0/CLEAR，关系5ns/data8.155ns/slack−3.738ns。
真实audio→pixel两路径：u_reset_sync/sync_chain_1_s0/Q至u_wave_bridge/u_mailbox/u_dst_reset/sync_chain_0/1_s0/CLEAR，关系5ns/data6.141ns/slack−1.309ns。

40MHz周期25ns和25MHz周期40ns来自相关PLL生成钟，工具这些路径最近有效关系只有5ns，并不提供一个整25/40ns周期的Recovery预算。pixel源reset输出已有约1355扇出，关键线约6.098ns，加组合和后段路由，导致上述负值。普通数据Setup的下一周期裕量与此5ns异步控制检查不能混为一谈。

源码连接：display_rst_n=visual_rst_n&&video_reset_done&&control_video_done；audio_rst_n来自audio本地域复位完成；bridge再次AND两者得到observation_async_rst_n，传入mailbox内部audio/pixel两reset_sync。各同步器都有异步清零、移入常数1的两级目标时钟释放。因此是“各域同步done再次组合成共享异步复位输入并重同步”的级联结构。

**重要分类补充**：这四个负端点全是reset_sync自身FF的CLEAR，不是同步器最终输出到业务FF的CLEAR。不能仅因Slack负就宣布音频复位释放必然不安全，也不能仅因模块名叫reset_sync就自动忽略它。需要证明：

1. 输入被设计为异步复位请求；同时清两级，目标时钟本地逐级释放，两级输出用途和ASYNC_REG/保留对象实际成立。
2. 同一观察mailbox在任一复位事件中双方均清request/ack，队列/窗口不让旧包复活；audio独立演奏链不得被显示复位牵连。
3. 两输入/LOCK的组合无需要捕获的短glitch、脉宽足够；任一域停钟时异步断言仍有效，恢复时不得提前把ready置高。
4. 同域多套复位同步输出的释放差异由source/pixel reset_done与source_up握手隔离，不把它们当完全同拍。
5. reset_sync第一级→第二级D Setup/Hold、同步后输出→业务FF的Recovery/Removal和脉宽仍完整检查。

满足这些证明后，可以在**另行受控新版本**研究精确异步复位入口例外，按实际起点和确认的四个同步器CLEAR脚覆盖，记录对象数和排除范围；这不等于删掉所有Recovery、整域falsepath或clockgroup，不能隐去业务复位或二级D路径。通用厂商复位同步器原则支持异步入口与同步本地释放分离，Gowin具体命令/对象及报告覆盖必须实查。本轮没有批准或加入任何新exception，现v2门禁仍失败。

若无法证明上述异步入口语义，或希望简化结构，优先在新集成副本改为明确common observation async reset根，各域各自释放；video/control initialized作为同步后的消费允许条件，而不是再把本地域done直接跨域拼成复位根。需要保留显示独立reset只flush观察支路、observer seq只随audio reset清零和PLL loss两边清的合同。任何接口/复位/CDC功能更改先列影响并按受控流程，补停钟/复位边界/旧包清理/音频等价自检，不沿旧9case宣称新逻辑已验。

单纯LOC缩短8.155ns有可能改善，但不会自动解决异步/同步路径分类问题，高扇出复位一味跨芯片拉线也不适宜作为首选。不能现在猜一个站点后反复route。

## 2. Hold：原音频路径只差11ps，但必须在原保护门槛下处理

真实路径frozen_base_56_s0/Q至g_lane[1].u_control/base_s0_24_s0/D，同一个40MHz sys_clk。

实际min-delay表：launch clock1.404ns；tC2Q0.144ns；数据线0.535ns；到达=2.083ns。
capture clock1.431ns；hold uncertainty0.650ns；cell hold0.013ns；要求=2.094ns。
2.083−2.094=−0.011ns，正向有效clockskew约27ps。原path表另以工具方向显示−0.027，计算使用实际launch/capture延时而不混淆符号。

它是数据到得过早，不是多加25ns周期能解决的数据到得过晚。频率降至更低并不能直接放宽同沿Hold；11ps虽小，也不能当舍入误差放行。本次650ps是明确保留的工程保护设置，物理实际减去这项后的裸cell裕量与工程门禁不是同一口径，不允许改650→600当作修复。

顺序：先重新核clocktree/同域Skew和相关路径group，确认原650ps约束仍正确；再针对这对真实endpoint进行合法位置/路由长度或工具hold修复控制，保持原lane2既有LOC，不扩大所有lane布局锁定。需要实际站点合法性/读回和新完整STA，不直接造LOC值。小于一个时钟周期的min-delay应由布线/物理实现策略处理，不能用不可综合#delay或新功能寄存器任意改变FCW/PCM代次。

修好这条后必须看全组端点，新增显示/同步器/SSRAM改变布局可能把最差短路径转移到别处。目标先守住全Hold≥0与TNS0，再取合理工程裕量；不只验一条链。

## 3. 为什么音频没改也出现新违例

v2只增加payload的syn_preserve，但全工程重新布局布线。真实映射observer从2BSRAM变0BSRAM+28SSRAM、mailbox多56寄存，Logic19149→20242/Reg9046→9109/BSRAM25→23，物理放置和时钟/控制扇出改变。原音频算法/ROM不变，只能说明逻辑语义未改，不能说明每个旧FF仍在原位置、旧Hold/Recovery仍成立。

原138K资源报告与新版Setup/STA不可混用。不是138K容量耗尽：本版Logic20242/138240、Reg9109/139095、DSP46/298；这个小比例不保证时序。瓶颈看局部跨域reset分发/min-delay/布局，不能把芯片余量当时序余量。

新payload56位24..79（seq32+left24）已有约束10ns/最差+8.5及三二段ACK/REQ/source_up非负，保留策略解决原TA2003有实际效果。右声道24低位因当前只显示左而优化，本结果不外推完整80位物理覆盖。
