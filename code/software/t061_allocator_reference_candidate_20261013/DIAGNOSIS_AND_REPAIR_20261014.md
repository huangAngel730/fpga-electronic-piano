# N32-A 编译故障诊断与未执行修复方案

本轮交付目标：可审核的诊断入口修复和下一次编译诊断计划。用户于
2026-10-14 明确授权主窗口与子智能体自行解决，暂停中间送审与 M2 复核；
本轮仍只准备，不执行新的 Icarus/VVP/EDA。旧 Q-0018/R01 保留为历史，
不将其中的意见或收件状态当作新版本通过证据。

## 诊断结论

两次实际 N4 编译均返回 `3221225477 / 0xC0000005`。
第二次已固定 suite/bin、suite/lib、系统 PATH 与 YOSYSHQ_ROOT，仍失败，
所以“仅补 DLL 搜索路径即可解决”的假设未得到支持。

两个失败窗口的 Windows Application 事件均有 `cmd.exe` 崩溃：
同一 PID 先出现 `ntdll.dll / 0xc0000008`，再出现
`msvcrt.dll_unloaded / 0xc0000005`。两窗口故障签名重复，
但尚未取得编译器内部阶段与该 PID 的完整关联，不能断言唯一根因。
同窗 ArmouryCrate 事件只记录相关性，不据此停用软件或修改系统。

现有命令长 497 字符、最大源路径 158 字符；没有支持路径长度超限的证据。
失败后残留的 `sim.vvp` 结构可读，但编译退出非零，不能使用它作为有效产物，
也不能运行该残留文件。

通过原冻结 Windows Job 监管路径运行的 direct cmd 与 Python→cmd 两个
软件探针均退出 0，总耗时约 0.062 秒。这排除了“所有这种 Job/cmd 调用
都会失败”的说法，没有排除 Icarus 特定子阶段、进程清理或外部软件交互。

## 本轮修复范围

诊断入口补齐执行前原字节 SHA 认证、父层 300 秒看门狗以及
`source_before/tools_before` 回执。父层限定私有子进程树，编译本身仍为
90 秒；失败与超时保留证据，次数固定为 1。

新的 compile-only 计划保留原 N4 三源字节与同一工具，编译参数仅新增
`-v`；capsule 路径随新版本重定位。这可以在下一次实际执行时记录 Icarus
内部阶段命令，进一步判定故障发生于预处理、代码生成还是 shell 收尾。
详细版本、源身份、启动命令与软件测试日志以同包 plan/config/launch 为准。

这修复的是诊断与证据机制。由于本轮明确保持未执行，不能宣称已经消除
Windows/Icarus 崩溃，也不能宣称 N32-A 功能通过。
