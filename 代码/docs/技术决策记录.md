## D008 三人岗位与所有权冻结

- 日期：2026-09-11
- 提议人：三人共同
- 状态：已冻结
- 问题：早期“音频核心、交互板级、软件验证”三分法把验证和交付责任分散，且 I2S 归属不清。
- 候选方案：按学科分工；按交付物分工；按数据流边界分工。
- 决策：采用 M1、M2、M3 三个岗位。M1 为音频算法、验证与竞赛交付负责人；M2 为 FPGA 技术与系统集成负责人并兼任技术与集成负责人；M3 为实体硬件、交互与上板验证负责人。FPGA 内的 DDS、波表、ADSR、复音、混音和数字效果算法按软件工作管理，归 M1。I2S 数字发送、时钟、CDC、顶层和约束归 M2。供电、电平、传感器、DAC、仪器测量归 M3。
- 依据：I2S 与约束本质是接口时序问题；算法验收需要单一责任人。
- 影响模块：全部；`代码/AGENTS.md`、`角色分工.md`、`协作入口.md`、各局部 `AGENTS.md` 的岗位名称与写入边界。
- 回退方案：若集成负荷过高，把 I2S 实现临时交回 M1，但约束和时序收敛仍由 M2 把关。

## D009 板卡与仪器资源分配

- 日期：2026-09-11
- 提议人：三人共同
- 状态：已冻结
- 问题：两套板卡和两台逻辑分析仪需要明确的编号、配对和配额，避免个人长期占用。
- 候选方案：完全自由使用；按人到固定编号；按周配额加共享池。
- 决策：BD-01 为稳定集成板，BD-02 为实验开发板，LA-01 默认配 BD-01，LA-02 默认配 BD-02。全部放在实验室，属于共享资源。两块板合计每周 40 小时配额：M1 六小时、M2 十四小时、M3 十小时、共同集成十小时。两台逻辑分析仪合计每周 40 小时配额：M1 四小时、M2 十四小时、M3 十二小时、共同集成十小时。配额是预约基准，未使用份额回到共享池。
- 依据：M2 承担集成和上板时序调试，板卡与分析仪需求最高；M1 以电脑端模型和验证为主。
- 影响模块：构建、上板验证和集成窗口安排。
- 回退方案：关键路径紧张时由三人同步会临时调整配额，并记录在资源使用记录中。

## D010 软件工作量分担规则

- 日期：2026-09-11
- 提议人：三人共同
- 状态：已冻结
- 问题：算法建模、验证脚本和上位机都算软件工作量，集中在一人会成为瓶颈。
- 决策：软件任务积压并影响关键路径时启动分担。M2 分担算法 RTL 的流水线、资源优化、FIFO、CDC、I2S 和构建工作；M3 分担按键、传感器、串口、仪器控制和数据采集软件。算法数学定义和最终验收始终由 M1 负责。
- 依据：保持算法验收单一责任人，同时释放实现带宽。
- 影响模块：任务看板的任务归属和复核关系。
- 回退方案：任务重新收回 M1 时需在任务看板注明原因和当前验证等级。

## D013 公共音频与演奏事件接口 v1.0 冻结

- 日期：2026-09-12
- 提议人：M2
- 状态：已冻结
- 问题：M1、M2、M3 及各自 AI 需要在不依赖会议和口头解释的情况下直接并行开发，原 v0.2 仍有待决项且事件结构只有 50 位。
- 决策：由 M2 直接发布 `模块接口规范.md` v1.0。事件固定为 64 位；Velocity 为 10 位线性；Note On Velocity 0 在输入侧转换为 Note Off；事件 FIFO 深度 32 并使用 valid ready 反压；连续控制入 FIFO 前限速和合并；PCM 为 24 位有符号二进制补码；I2S 使用 32 位槽位和 24 位有效数据；复位低有效、异步拉低、同步释放；`sample_tick` 为 48 kHz 单周期计算请求；第一版使用单 `sys_clk` 加时钟使能。
- 发布方式：初始 v1.0 不要求 M1、M3 额外确认或签字，仓库中的接口文档即为执行依据。M1、M3 负责按接口实现并反馈实际影响，不设置阻止初始基线发布的前置门槛。
- 依据：接口是并行开发的前置条件；由 M2 统一建立初始基线，可以避免会议等待和不同 AI 生成不兼容接口。
- 影响模块：输入模块、事件转换、音频核心、混音器、顶层、I2S 发送、公共测试桩与持续集成。
- 后续修改：M1 和 M3 提供影响分析，M2 决定是否发布 v1.1 或 v2.0；任何功能分支不得私自改变公共接口。
- 回退方案：若实际资源、时序或外设证明某项不可行，由 M2 发布新接口版本并组织同一集成窗口迁移，不回退到口头约定。

## D014 引导期直推例外

- 日期：2026-09-12
- 提议人：M2
- 状态：暂定
- 问题：`Git协作规范.md` 规定 `main` 禁止直接提交、`develop` 只接受通过复核的功能分支合并。但治理文档本身只存在于 `docs/eight-week-plan` 分支，尚未进入 `develop` 和 `main`；此时 M1、M3 尚未接入仓库，不存在可用的非作者复核人，走合并请求流程在客观上无法成立。
- 候选方案：等复核人接入后再按规范走合并请求；由仓库所有者在引导期直推并事后登记例外；永久放宽 `main` 的分支保护。
- 决策：采用引导期直推。由 M2 以仓库所有者身份，将 `develop` 与 `main` 快进到 `docs/eight-week-plan` 的顶端提交，并把尚未开工的分支对齐到同一提交。全过程仅使用快进，不使用强制推送。
- 依据：引导阶段没有可用复核人，规范无法执行；先建立所有队员共享的同一基线，再让规范正式生效，优于让规范在空转中被绕过。此例外必须显式登记，否则 Git 历史将与 `Git协作规范.md` 产生直接矛盾。
- 影响模块：全部分支的起点、`Git协作规范.md` 的写入规则、后续合并请求的复核关系。
- 生效范围：仅限仓库引导阶段，截至 M1、M3 完成协作者接入并成功 clone 仓库。
- 退出条件：M1、M3 接入后立即为 `main` 和 `develop` 启用分支保护，并勾选不允许绕过设置；此后所有改动必须走合并请求与非作者复核，包括 M2 本人。
- 回退方案：队员接入前若发现文档存在事实性错误，允许在引导期内继续直推修正；队员接入后只能通过新提交修正，并保留原提交历史。
- 待办：三人确认后改为已冻结；M1、M3 接入后由 M2 开启分支保护并在本条目追加实际开启日期。
