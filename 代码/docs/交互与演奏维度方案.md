# 交互与演奏维度方案

状态：**草案，未冻结**。对应任务拟编号 T050，决策拟编号 D017。

起草日期：2026-09-12。起草人：M2。

本文件回答一个问题：在两个月工期内，做什么样的演奏交互，既能满足赛题基础要求（≥2 个独立可控维度）和拓展要求（≥3 维表情调控），又不至于做不完。

## 一 赛题原文要求

基础要求原文：

> 系统依托电容触摸、光电感应、压力检测、无接触手势等**任意自研交互方案**，实现至少 2 个独立可控演奏维度的动作采集，精准识别选音、和弦、触发、拨弦等演奏指令。

拓展要求原文：

> 自主设计演奏交互形态，基于各类传感器实现演奏动作精准采集，支持选音、触发、拨弦、**力度感应**等操作，具备**至少 2 个独立可控维度**，交互逻辑灵敏稳定，适配乐器演奏场景。

> 搭建 **≥3 维演奏表情调控逻辑**，支持**力度动态、滑音、颤音**等演奏效果；支持 ≥2 种乐器音色自由切换。

## 二 方案选型与合规性论证

### 2.1 候选方案

| 方案 | 维度来源 | 工期风险 | 自研含量 | 演示直观性 |
|---|---|---|---|---|
| A 全自研键盘矩阵 | 自建扫描与力度检测 | 中 | 高 | 高 |
| B 外购 MIDI 键盘直读 | MIDI 流解析 | 低 | 低 | 高 |
| C 外购键盘硬件 + 自研扫描 | 自研扫描与力度算法 | 低 | 中高 | 高 |
| D 电容触摸 / 光电 / 手势 | 自研传感器 | 高 | 高 | 中 |

### 2.2 选定方案：C

选定 **方案 C：使用外购力度键盘的键盘总成作为机械与电气部件，扫描、去抖、力度解算、事件转换全部自研**。

### 2.3 为什么不是方案 B

方案 B（买成品 MIDI 键盘直接读 MIDI 流）工期最省，但存在实质风险：

- 赛题原文写的是"**自研交互方案**"。整机直读 MIDI 时，交互环节退化为协议解析，与"自研"导向不符。
- 答辩时会被问"这部分你们自己做了什么"，难以给出有分量的回答。
- 作品的核心创新点会集中到算法侧，交互侧成为外购件的搬运。

因此本方案**不采用直读 MIDI**。

### 2.4 方案 C 的自研内容清单

以下部分由本项目自行实现，构成答辩时可说明的工作量：

| 自研内容 | 归属 | 说明 |
|---|---|---|
| 键盘矩阵扫描与去抖 | M3 | 自建扫描状态机，不依赖键盘内部电路 |
| 力度解算（双触点时间差） | M3 | 自建测时与映射算法 |
| 统一事件转换 | M3 | 映射为 `performance_event_t` |
| 踏板/弯音轮采集 | M3 | ADC 或开关采样与滤波 |
| 和弦识别 | M1 | 依据同时进入的 Note On 判定 |
| 拨弦判定 | M1 | 依据力度与触发包络特征 |
| 全部合成算法 | M1 | 与交互解耦 |

**关于 MIDI 协议**：接口规范 3.2 节已定义 MIDI 7 位 Velocity 到 10 位的映射，说明项目本来就为 MIDI 兼容预留了能力。方案 C 不排斥 MIDI —— 若键盘总成自带 MIDI 输出且无法直接引出扫描线，则**在自研适配层中解析 MIDI 并转换为统一事件**，这仍属自研适配层的一部分，但自研含量低于直接扫描，需在答辩材料中如实说明。

### 2.5 待核实

## 三 演奏维度定义

第一版定义三个维度，与赛题的 R1、R6、R7 对应。

### 维度 1：选音（对应 R1、R2）

| 项目 | 内容 |
|---|---|
| 物理来源 | 键盘按键位置 |
| 事件字段 | `note_number`（7 位，0 至 127） |
| 更新方式 | Note On / Note Off 离散事件 |
| 接口编码 | `EVENT_NOTE_ON`（0）、`EVENT_NOTE_OFF`（1） |
| 键盘规模 | 25 键，两个八度 |
| 音域 | 待定，建议 C3 至 C5，覆盖演示曲目 |

25 键而非 13 键的理由：演示曲目通常需要两个八度；25 键的接线量（两组矩阵约 20 线）在 GW5AT 可用 IO 范围内；再往上（49 键以上）扫描矩阵与接线复杂度上升明显，超出两个月工期的合理范围。

### 维度 2：力度（对应 R6、R1 的第二维）

| 项目 | 内容 |
|---|---|
| 物理来源 | 键盘双触点闭合时间差 |
| 事件字段 | `velocity`（10 位，1 至 1023） |
| 更新方式 | 随 Note On 一次性给出 |
| 接口编码 | 承载于 `EVENT_NOTE_ON` 的 `velocity` |
| 无力度时的退路 | 固定值 512，保持接口语义不变 |

力度是 R1 要求的第二个独立维度：同一个键按下轻重不同，输出不同，满足"独立可控"。

**力度解算待定项**：时间差到 velocity 的映射曲线（线性或对数）、时间差测量范围与分辨率、按键机械抖动对双触点的影响，均需 M3 在 T050 中实测标定。可参考机械键盘与电子琴力度的通行做法，但必须实测，不得照抄。

### 维度 3：延音踏板或弯音轮（对应 R7、R8）

| 项目 | 内容 |
|---|---|
| 物理来源 | 延音踏板开关 或 弯音轮电位器 |
| 事件字段 | 踏板用 `control_value`；弯音轮用 `control_value` 有符号 |
| 接口编码 | 踏板建议新增 `CTRL_SUSTAIN`；弯音轮用已有的 `CTRL_PITCH_BEND`（0） |
| 更新方式 | 离散事件或限速连续事件 |

**优先做弯音轮**，理由：接口规范 3.2.1 节已完整定义 `CTRL_PITCH_BEND` 的语义、中心点和弯音范围，无需新增接口定义，实现路径最短，且直接满足 R8（滑音）。

延音踏板作为备选：若使用普通开关，只需一个 GPIO，成本极低，但需要在 3.2.1 节新增 `CTRL_SUSTAIN` 编码。是否采用取决于 M3 的硬件进度。

## 四 需实测的指标

以下指标必须在 T036 实测，不得凭估计写入对外材料：

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 按键到事件延迟 | ≤2 ms | 逻辑分析仪测触点闭合到 `event_valid` |
| 去抖时间 | 待标定 | 示波器观察触点抖动 |
| 力度分辨级数 | ≥16 级 | 逐级按压记录 velocity |
| 力度重复性 | 同力度偏差 ≤10% | 同一力度重复 30 次 |
| 连续控制更新率 | ≤1 kHz | 受接口规范 3.7 限制 |
| 和弦识别同时性窗口 | 待定 | 依据人手生理极限，建议 30 至 50 ms |

**与接口规范的衔接**：接口规范 3.7 节规定单一连续控制源更新率不超过 1 kHz。三维度中只有维度 3 属于连续控制，1 kHz 对其足够（颤音通常 5 至 7 Hz，弯音手速远低于 1 kHz）。因此接口限制不构成瓶颈。

## 五 与现有差距的对应

本方案解决的差距（编号见 `赛题要求对照表.md`）：

| 差距 | 原本问题 | 本方案的解决方式 |
|---|---|---|
| G1 | 交互维度无设计任务，T036 排到 W6 | 本文件即维度设计，见下方排期说明 |
| G3 | velocity / expression 无传感器来源 | 维度 2 提供 velocity 来源；expression 见 5.1 |

关于 G1 的排期说明：W3 已排入 T021、T022、T015 三个 M3 任务，不宜再插入新任务造成过载。建议的处理方式是把 **T036 的冻结时间从 W6 提前到 W4**，并让 T050 的产出物（键盘选型、力度标定方案）作为 T036 的输入，而不是新增一条并行任务线。T036 是基础要求的冻结节点，排在 W6 确实偏晚。

### 5.1 关于 expression 字段的说明

接口规范中 `expression`（10 位）与 `control_id` 的 `CTRL_MODULATION` 存在语义重叠，该问题已在接口审查中记录但尚未澄清。本次交互方案**不依赖 expression 字段**：

- 力度走 `velocity`
- 弯音走 `control_value`（`CTRL_PITCH_BEND`）
- 颤音走 `control_value`（`CTRL_MODULATION`）

即三个维度全部通过**已定义的字段**承载，不引入新的未定义语义。`expression` 的定位问题留待接口澄清时一并处理。

### 5.2 关于 R9 颤音

`CTRL_MODULATION` 编码已存在，但"调制轮到颤音深度与速率"的映射属算法侧，需 M1 定义。本方案只保证**输入侧能产生该事件**，不承诺音效听感。
